# 知衡：同类项目调研与完整服务流程改造

日期：2026-09-21。状态：调研与实施设计，本文的新设计尚未实现。现有交付仍为 0.4.0。

## 1. 结论

当前最重要的问题是：系统擅长收集字段和生成文本，但还没有稳定地把“证据、判断、行动、反馈”连起来。增加早餐、午餐、晚餐问题能补缺口，却不能自动形成专业咨询。

产品目标应是：了解用户当下要解决什么，在必要信息足够时共同选定可执行的小改变，记住实际发生的事，发现困难后调整，并能解释每次判断的依据。问得多、方案长、数字精确，都不能作为专业度的替代指标。

保持独立安卓应用和本地存储。借鉴其他项目的业务结构，不直接搬入多服务服务器架构，也不为了显得完整一次加入穿戴设备、购物清单等外围功能。

## 2. 调研范围和证据边界

本轮阅读下列项目公开 README/功能说明及官方营养管理资料，并对照本项目实际代码。没有安装运行这些第三方项目，没有验证其宣传效果；功能说明不代表临床有效性，也不代表适合中文饮食。以下“借鉴”是本项目设计判断。

| 来源 | 公开资料显示的能力 | 值得借鉴的设计 | 采用边界 |
|---|---|---|---|
| [wger](https://github.com/wger-project/wger) | 饮食、体重与身体测量、训练管理；使用 Open Food Facts；提供 API | 记录、计划、趋势分别管理，长期积累 | 健身管理系统，不是现成的营养咨询流程；不整体迁入 APK |
| [kcal](https://github.com/kcal-app/kcal) | 自定义餐次及目标、食物和食谱、饮食日记；历史日记保留营养快照 | 餐次顺应生活；修改食谱不改写过去实际记录 | 作者明确不提供饮食指导；其灵活记录结构值得借鉴 |
| [OpenNutriTracker](https://github.com/simonoppowa/OpenNutriTracker) | 移动端食物日记、搜索和扫码、常用食谱、趋势、数据导入导出 | 降低重复记录成本；给用户可查看、可纠正、可带走的数据 | 日记工具不能替代咨询；食物库对中国菜的覆盖需另测 |
| [Luma](https://github.com/d3mocide/Luma) | 声称支持餐次替换、计划、聊天工具调用、趋势及周总结 | 聊天调用独立数据能力；计划可局部替换；执行后有总结 | 本轮只核对公开说明；多服务部署不适合直接嵌入；不能据此宣称建议可靠 |
| [Wellness Nourish](https://github.com/davidmosiah/wellness-nourish) | 食物查询、照片辅助、记录预览、日志、日周汇总；区分照片线索和保存 | 识别结果先有证据与状态；查询、估算、记账是不同动作 | MCP 工具，不是完整手机产品；无需照搬逐次手动确认，沿用知衡明确陈述自动保存的约定 |

[Academy 的 Nutrition Care Process](https://www.eatrightpro.org/practice/nutrition-care-process)包含评估、营养诊断、干预、监测与评价。知衡借鉴其持续评估结构，把面向用户的判断呈现为“问题与依据”，不把模型推断冒充临床诊断。

[NIDDK 的项目选择指南](https://www.niddk.nih.gov/health-information/weight-management/choosing-a-safe-successful-weight-loss-program)强调个人情况、可坚持的安排、支持与持续监测；[行为改变资料](https://www.niddk.nih.gov/health-information/diet-nutrition/changing-habits-better-health)强调小目标、记录感受、处理障碍和重新开始。因此，复盘应该能改变下一步安排，而不只是生成鼓励文字。

## 3. 当前实现的根本缺口

| 代码/证据 | 当前行为或局限 | 后续要求 |
|---|---|---|
| `intake.py:QUESTIONS/missing`；`product.py:chat` 的建档分支 | 主要按缺失字段顺序追问；有缺口时阻止正式计划，初步方案例外 | 按具体决策判断资料是否足够；优先追问影响当前行动的问题 |
| `intake.py:known/has_portion` | 有份量词即视作餐次信息较完整 | “一碗面”不能证明已知道面量、配菜、饮料、频率；分别保留未知，也不能每项都强制追问 |
| `product.py:chat` | 一轮同时处理提取、访谈、计划、页面、保存与错误 | 事实保存和建议生成分开验收；后者失败不应让前者不明不白 |

| `storage.py` | SQLite 保存 JSON 文档，已有事务与修订能力 | 保留底座，增量引入事实来源、有效期、状态和评估引用，不为重构清空资料 |
| 0.4.0 真实模型交接记录 | 链路通过，但仍出现未经支持的份量和精确营养数字 | 用结构校验和受控计算约束方案；不能再以增加提示词视为修复完成 |
| 0.4.0 照片验证记录 | 浏览器转换、队列、合成图片模型调用通过；真机相机尚未覆盖 | 相机启动、回传、进程恢复、保存和重试分别验证 |

2026-09-14 的产品设计已经提出动态追问和持续跟进，但缺少足以约束实现的验收条件。这次保留原有对话驱动、自动整理档案与独立方案页方向，补齐决策规则，不重新发明一套导航。

## 4. 完整用户旅程

### 第一次：理解诉求，决定下一步

先了解用户此刻想解决什么、希望改变什么以及最大的困难。结合已有资料核对基础情况、相关健康限制和现实条件。年龄等明确答案即时保存，回答中主动提供的其他信息一起整理，不能问一项只记一项。

每次最多围绕一个主题自然追问。用户提到手术后不适，优先澄清手术与当前限制；用户只想记午饭，先完成记录；用户没有时间长聊，提供阶段总结和下次继续入口。必要信息缺失时限制需要该信息的判断，而不是堵住全部功能。

“足够”的判断按用途划分：记录一餐、讨论一种可行替换、制定个体营养目标，所需证据不同。跳过疾病问题代表未知，不能变成无疾病；只知道年龄也不能支持精确热量目标。

### 了解饮食：还原真实模式

先让用户描述有代表性的一天，再补会改变判断的缺口：实际有几次进食、每次食物饮品与大致份量、工作日和休息日差异、外食条件、容易饿或吃撑的情境。以用户实际餐次为准，适应两餐、轮班和加餐，不强制所有人三餐。

区分“平常这样吃”“昨天这样吃”“举个例子”“打算这样吃”。用户给菜名后，要弄清这是常见搭配还是偶尔选择，而非直接写入每日菜单。不了解的份量保留未知，照片也不能确定隐藏油量和实际吃完比例。

访谈结束前给简短摘要：已经了解什么、当前可能的困难、还不能确定什么。允许一句话纠正，避免把推断写成用户事实。此前已明确保存的信息无需再逐项点击确认。

### 制定方案：从依据到行动

每项方案必须表达：针对什么问题、依据哪条记录、准备做什么、何时适用、现实中怎么替换、用什么反馈判断是否有用。先共同选定少量可执行行动；具体多少取决于用户能力，默认从 1–2 项开始是产品策略，不是医学标准。

方案以相对生活事件安排，用户给出固定时刻时才使用具体时间。区分下一次进食建议、当天剩余安排与以后完整计划。默认次日开始仍可保留，但要明确生效日期；当天已吃过的内容不要求补做或补偿。

没有可靠来源的热量、营养量和份量不得作为精确结论。允许无数字的行为方案；需要数值时必须由可追溯的数据与计算产生，并说明估计及适用条件。

### 每天：减少记录负担，解决当下困难

再次打开应用，首先显示与当前时段相关的下一步、需要核实的事项及最近变化。明天起床应提供什么由前一天约定决定，不要求所有人每天重报完整档案。

支持常吃餐复用、文字简记、拍照补份量；用户说“和昨天一样”时核对必要变化即可。把记录完整度和执行结果分开：没记录不是没吃，也不是没执行。

遇到出差、加班、聚餐或不想执行，先了解阻碍，提供可选替代或缩小行动。临时改变只覆盖有关日期，不重写长期方案；不以额外节食或运动作为惩罚。

### 复盘：用证据决定保持还是调整

到约定复盘日，汇总实际记录覆盖率、用户感受、执行障碍和可比较的趋势。资料不足先指出不足；短期体重变化不能自动触发削减饮食。

复盘结果必须落到保持、替换、降低难度、补充观察或建议专业支持中的具体下一步，保留原因、适用日期和上版方案。中断后回归，从当前情况恢复，不责备、不要求补齐所有漏记天数。

## 5. 支撑流程的数据与职责

以下是实施设计，不代表新增模块已经存在。

| 对象/职责 | 最少需要表达什么 |
|---|---|
| 事实 | 值、单位、实际发生时间、记录时间、原话/照片来源、明确/待核实/已纠正状态；习惯和单次事件分开 |
| 访谈状态 | 当前目标、问题 ID 与主题、为什么问、已回答内容、缺口、跳过偏好；跨会话继续，不靠猜上一句文字 |
| 评估 | 关注问题、证据引用、仍未知部分、允许进行的决策、需先澄清的事项 |
| 方案版本 | 目标、行动、适用日期和生活事件、替代项、反馈指标、复盘条件、产生它的评估 |
| 实际记录 | 与建议分开；修改有历史，重复提交不重复累计；营养估算保留来源与当时快照 |
| 模型职责 | 理解自然语言、提议事实候选、解释和提出备选；不能自行把估计升级为确认事实 |
| 程序职责 | 保存、状态流转、日期、单位和数值计算、证据校验、限制无依据输出、错误恢复 |

事实接收与建议生成分别返回结果。示例：年龄保存成功而计划被拒绝，应明确显示年龄已经入档及计划暂未生成；重试只处理未完成部分。照片任务同样区分上传、识别、核实与记录，不把失败全部显示为“模型未完成”。

食物数据接入先做中文常见菜、份量单位、生熟重和外卖场景验证。不能把外国数据库查到的同名菜直接当作用户实际餐食。可靠匹配不足时保留原话，使用区间或不提供数值。引入第三方代码或数据前另查许可证与再分发条件。

## 6. 实施顺序与完成条件

1. **先建立可信的数据链路。** 事实保存与建议错误分离；问题 ID 对应答案；档案、回执与重启后读回一致；照片各阶段可诊断和恢复。真机未验证不能标成拍照问题已解决。
2. **再替换固定访谈推进。** 建立按当前决策选择追问的状态模型；有意义的阶段摘要；安全相关未知控制相应建议；允许先记录、分次了解和继续原对话。
3. **约束方案依据与计算。** 方案行动关联证据；删除无依据数字；日期和个人餐次由程序约束；模型输出不合格时保留已存资料，给可理解的下一步。
4. **打通执行与复盘。** 今日下一步、常用记录、临时替代、约定反馈和版本化调整。先做应用内引导；系统通知作为独立能力实现和验证，不能把打开页面显示当作推送。

每阶段先通过对应场景再发布，避免所有改动一起堆进 APK。首个阶段以可靠性为主，不宣称已经达到专业咨询质量。

## 7. 验收从功能数改为连续生活场景

| 场景 | 必须满足 |
|---|---|
| 晚上首次使用、时间有限 | 已说信息保存；说明阶段结论；安排未来可做的事；下次接续，不重复全套问题 |
| 回答年龄后模型断网或计划触发安全规则 | 已确认年龄可在档案读回；明确失败阶段；重试不重复入档 |
| 轮班、每天两餐 | 使用个人餐次和睡眠安排，不硬塞常规三餐或固定钟点 |
| 用户举例、准备吃、实际吃、替别人拍 | 四类信息不互相混淆，纠正后统计同步改变 |
| 模糊照片、部分食用、饮料未入镜 | 不编造克数；补最必要的问题；纠正同一餐，不叠加另一餐 |
| 加班或聚餐导致方案做不到 | 提供现实替代，保留未受影响的安排和既有完成记录 |
| 两天未记录后回来 | 未记录显示未知；从当前恢复；不作失败评价 |
| 一周回顾、记录不全、体重波动 | 显示证据不足，结合执行体验调整，不凭单日数字自动收紧方案 |
| 修改常用食谱 | 新记录使用新内容，旧餐保持当时事实与估算快照 |

测试分层：数据不丢失/不重复的自动化回归；真实模型多种措辞的案例评审；连续七天模拟使用；安卓真机相机和进程恢复；营养建议内容的独立专业评审。前两天可以先验证流程，七天模拟只能验证复盘逻辑，不能证明减重效果。

验收记录分别报告事实正确率、无依据结论、重复追问、行动与证据对应、纠正传播和用户操作负担。出现关键事实丢失、虚构已吃记录、危险建议或无依据精确处方，应阻止该版本通过。单元测试数量只说明技术回归覆盖，不代替这些结论。
