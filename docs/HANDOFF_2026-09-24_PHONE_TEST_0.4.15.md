# 知衡 0.4.15：可核查餐图估算与单对话导出

日期：2026-09-24。私人手机测试包。用户的目标是让首次咨询更像持续了解情况的营养师，并能看到照片中可能有什么、粗略热量、计算方法、来源与下一步建议。本轮根据多人分食照片和一次完整模拟访谈修复；不将模拟中的真实健康信息写入测试资料或文档。

## 交接状态与判断

**可交给用户做真机验收，不能宣称营养师体验已经验收通过。** 0.4.15 已打包、签名和核对，代码回归与隔离 UI 流程通过。当前模型仍为 `claude-opus-4-8`。这次模拟中最明显的问题是应用层把安全资料收集做成了问卷、在早期建议上反复兜底，以及餐图数字缺乏可核查依据；同条件小样本换模没有解决这些问题，所以暂不改模型。用户测试后，应先看导出的真实对话，再决定调整规则、数据源或模型。

本交接只涉及程序和虚构测试资料。项目 `.data` 内的真实健康资料未被改动或打包；不要把用户在模拟中的病史、用药和饮食照片抄进仓库测试用例。

## 本轮改动

- 单一食材采用本机内置、逐条核对的 [USDA FoodData Central](https://fdc.nal.usda.gov/api-guide/) SR Legacy 参考快照。目前仅有熟米饭、生茄子、食用油、熟鸡肉带皮、炖牛肉五个严格匹配条目。程序仅在名称和生熟口径匹配时使用其每 100 g 数值；每项报告显示可食重量假设、公式、数据库条目编号和官方查询链接。餐馆复合菜、调味油和酱汁仍须说明估算依据或保留未知，数据库食材不等于这道菜实测。
- 某项重量或营养未知时，整餐相应总量不显示为完整值；界面单列“已估算部分”，提示未识别的油、酱汁等可能造成遗漏。模型不能自行声明已经核对包装标签或 USDA 条目。正面“0 脂”不足以得出整瓶热量、糖或咖啡因。
- 照片自动分析不猜人数或本人食用比例。明确关联照片后，多人分食、只吃一点可记录确实吃过，但热量保持未知；只有用户明确说出可核对的比例并确认，才按照片粗估换算。编辑报告与记录实际摄入分开。
- 访谈中的正式计划仍需安全资料与摘要核对，但聊天会先回应本轮困难，允许一项低风险起步选择；不再只能复读问卷。对活动中喘、晕的叙述提示停止诱发动作并线下评估，不安排跑步或冲刺；明确自述的用药与病史分字段保存，避免重复追问。
- 对话页新增“导出本对话”。生成 JSON，包含本对话每轮原话、回复、时间、连接/回退/流程状态及关联图片的文字分析与营养报告。它不包含其他对话、完整档案、原图、模型配置或密钥。分享前用户应自行查看原话中的隐私；导出只下载到手机，不自动上传。

## 代码入口与数据流

- 餐图：`server.analyze_image()` 调视觉模型识别；`server.normalize_image_analysis()` 把模型的结构化描述交给 `nutrition_reports.py`；`food_catalog.py` 只为精确匹配的普通食材提供来源值；`nutrition-report-ui.js` 展示估算、假设和来源。图片本身不证明用户吃过，报告也不是实际摄入记录。
- 摄入确认：`report_editor.py` 对手动改重量、来源和食用份数做预览与重算；`workbench.py` 对聊天中的本人食用陈述做落地校验。“没吃多少”是吃过但比例未知，不能把模型填的整盘热量沿用到本人记录。
- 初诊：`consultation.py` 保存评估门槛与有限的起步建议；`product.py` 生成访谈提示、保存有原话依据的资料，并在模型给出过早或不安全的内容时回退。查“模型明明回答了、界面却像问卷”时，重点检查 `product.py` 的 readiness/prose guard，不能只调模型提示词。
- 导出：对话页 `app.js` 调用 `GET /api/conversation-export?id=...`；`server.conversation_export()` 只挑选单个对话的消息、有限诊断字段及其关联图片的**文字报告**。旧的“导出数据”和“下载完整备份”仍在设置页，范围与用途不同。

## 如何用导出对话定位问题

用户在对话页选择相应历史对话，点击“导出本对话”，会得到 `知衡-对话-日期-会话短 ID.json`。文件是只读副本，不会修改或上传本机数据。它不含原图；餐图识别有争议时，请用户另附对应照片或截图。接手者先按 `messages` 顺序找用户原话与助手回复，再看该助手消息的 `diagnostics`：

1. `ai_status` / `ai_error` 判断是模型连接失败、回退还是已连通；`upstream_model`、`request_id`、`elapsed_ms` 用于定位服务调用。若没有请求标识，不要臆测模型超时。
2. `decision`、`workflow_warning`、`food_error`、`page_error`、`background.failed_operations` 判断是否在应用校验或保存阶段改变了结果。导出的是**最终可见回复**，不含模型未通过校验的原始草稿或内部推理；要区分模型原话与程序兜底，需在隔离环境复现。
3. 关联图片查看 `attachments[].summary` 与 `attachments[].report`，核对食材、份量依据、未知项和来源。先问用户是历史照片还是当餐、几人分食、本人吃了多少；不要用整盘热量直接计算个人日摄入。

导出中可能有用户主动说出的病史、用药和餐食信息，分享前由用户自行检查；不要把导出文件、照片或真实资料提交到源码仓库。

## 模型判断与验证

- 当前 `claude-opus-4-8` 与备选 `claude-opus-5` 用相同虚构初诊案例各测试三轮。两者均能连接且不会提前保存计划，但都出现过冗长列问卷或被应用兜底规则替换回复的情况；备选模型未显示足够明确的改善，因此本包继续使用当前模型。这是小样本质检，不是模型能力排名。
- 244 项 Python 回归通过；隔离窄屏 UI 流程通过，含单对话 JSON 下载、餐图报告核对、实际食用确认和撤销。模型实测与 UI 测试使用虚构资料及临时数据库，没有触碰项目 `.data`。
- Android release 编译和 lintVital 通过。无已连接的 adb 手机，本轮尚未验证用户手机上的系统下载、真实餐图识别质量、语音权限和长对话体感；这些由用户覆盖安装后测试。

验证入口：Python 回归在 `tests/test_*.py`；餐图、分食和来源边界见 `tests/test_nutrition_reports.py`、`tests/test_report_editor.py`、`tests/test_image_jobs.py`；单对话导出白名单见 `tests/test_server.py`；窄屏下载与编辑流程见 `tests/qa_nutrition_flow_ui.py` 和 `tests/qa_nutrition_flow_ui.mjs`。`tests/qa_model_compare.py` 用临时目录和虚构案例比较模型，不能把三轮结果当作统计结论。

## 尚待验证及下一轮优先级

1. **真机下载和分享**：确认 Android WebView 中“导出本对话”能保存 JSON，历史对话切换后导出的是所选会话；若 Android 系统下载器拦截，应修原生下载链路。当前只有隔离 Edge 窄屏流程通过。
2. **真实餐图质量**：五个 USDA 单食材条目覆盖面很窄，餐馆铁锅鸡、咖喱、茄子等复合菜的食材重量、油和酱汁仍可能严重偏差。需用用户允许分享的照片及导出对话复盘：识别是否正确、区间是否过窄、未知是否显眼、建议是否接住个人限制。不要凭一张照片宣称精确热量。
3. **长对话自然度**：检查是否重复问已回答的病史/用药、能否记住工作时间和食物偏好、评估中是否给出一项有帮助而不过界的选择。若 `ai_status=connected` 但回复模板化，先查兜底与资料字段；若是模型原始输出冗长，再设计同条件更多样本比较模型。
4. **麦克风**：0.4.14 的原生识别改动已保留，但首次授权、拒绝后恢复和具体手机上的识别质量还没由本轮真机复测。

下一轮不要直接替换模型或扩大食物库。先以真实导出建立可重复的失败案例，按“识别错误 / 来源值错误 / 份量错误 / 食用归属错误 / 对话兜底错误”分别修复，并再次用隔离资料测试。
