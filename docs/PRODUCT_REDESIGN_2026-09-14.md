# 知衡：对话驱动的个人减肥工作台

日期：2026-09-14。状态：设计提案，尚未实施。

依据：最新交接 `HANDOFF_2026-09-07_PRODUCT_V2.md`、旧产品设计与需求文档，以及用户本轮明确澄清：AI根据每次对话判断是否更新方案页面，包括文字、图片、图表、模块与看板；档案同样持续更新。

本文作为下一轮实施设计提案。已实现能力仍以代码和交接中的验证事实为准。旧 ARCHITECTURE.md 中“无数据库”等描述已过时，不能据此重新迁移正式资料。

## 1. 设计结论

需要重设计业务编排和页面内容模型，不需要推倒整个项目或先更换模型。

产品从“对话生成若干计划事项”改为“通过对话维护一份长期个人档案、一份当前方案和一个每日看板”。每轮输入都评估是否产生事实、是否影响方案、是否需要页面内容变化；没有变化也应是有效判断。

完成标准：聊天结束后，适当的文字、照片、图表和安排在对应页面出现或更新；刷新、新会话、服务重启后保持一致；能够知道为何更新并纠正错误。

## 2. 用户看到的页面

主导航为“今日、对话、方案、档案”；设置通过常驻设置入口进入。首次使用默认进入对话；形成方案后默认进入今日，也可保留用户上次页面。

| 页面 | 内容与职责 | 更新方式 |
|---|---|---|
| 对话 | 文字、语音、照片，同一条时间线；首次了解、每日交流；简短回复及更新回执 | 一次输入可触发多个页面更新；回执可跳到发生变化的模块 |
| 今日 | 今日重点、实际记录、适用安排、饮食照片、进展趋势、最近调整 | 读取保存后的内容及派生数据；日期切换更新当日内容，不自动编造新方案 |
| 方案 | 当前目标、个人情况摘要、饮食策略、活动安排、作息、替代方式、复盘与调整历史 | AI按需要新增或修改模块，保留未受影响部分 |
| 档案 | 基本信息、健康背景、生活条件、目标、按日期的事实记录和媒体、来源与待核实项 | 明确陈述整理入档；照片候选和歧义信息带状态展示 |

方案是长期可读的完整页面，不再把全部内容塞进看板一张计划卡。今日是摘要和执行入口，完整方案和完整档案均可单独查看。

## 3. 首次了解与持续跟进

首次了解按用户维度持久保存状态，而不是每个新会话重新开始：了解中、初步方案、持续跟进。各主题记录已知、待核实、未了解、用户跳过及来源。

主题包括身体基础与近期变化、本人自述健康背景、饮食习惯、日常活动、睡眠、生活约束、目标与偏好。每轮只问最有价值的一个问题，允许一次回答多项、文字与语音混用、随时补充或跳过。表单降为可选辅助。

不能因出现一条体重记录就认定整体了解完成。模型提出下一问题及理由，程序检查已有信息和跳过状态，避免重复追问。没有充分资料时允许初步方案，明确未知信息；不能把“未知”写为“没有疾病”等事实。

已有用户从现有档案继续补充，不清空、不照搬旧需求中的示例画像，也不要求重复完整访谈。用户只想记录或问一般问题时正常处理，不强制进入访谈。

## 4. AI如何决定页面变化

每轮获得本次输入、相关档案、当前方案及模块版本、当天记录、有关历史记录和计算好的趋势。返回结构化的事实候选、跟进状态、评估决定、模块变更和简短回复。

| 判断 | 页面行为 | 示例 |
|---|---|---|
| 无需变化 | 不新增模块、不增加方案版本 | 普通知识问答或重复表达 |
| 新事实 | 更新档案和相关今日视图，方案可保持 | 新测量或明确进餐记录 |
| 新解释或材料 | 补充方案文字、照片说明、证据或图表模块 | 结合用户常见午餐说明可行的选择 |
| 当日临时调整 | 创建有明确日期的覆盖安排，今日展示原因 | 明天出差，暂时换成便于执行的安排 |
| 长期方案调整 | 修改受影响模块和未来适用安排，生成方案新版本 | 工作时间长期变化导致原安排不适用 |
| 信息不足 | 提出一个必要问题；已验证事实仍可保存 | 无法确定照片是否本人已经吃过 |

上述判断由每轮语义评估产生，不能用是否出现“修改”二字决定是否允许更新。普通记录不必导致方案改动；达到复盘条件时利用新证据评估，不默认重写全文。

默认自动保存并显示合理的内容和模块更新，不要求用户每次说“保存到看板”。改变已启用方案的未来安排须明确显示生效范围及调整原因，保留撤销入口。仍尊重用户暂停计划、逐次确认设置以及“先讨论、别记录”的要求。删除整份资料不属于普通页面更新。

页面内容版本与执行计划版本分开：新增解释、照片或图表不能重建任务或改变完成记录；只有行动内容、适用日期等实质变化才更新执行计划版本。不能每更新一个标题就产生一套新任务。

## 5. 页面模块协议

稳定页面框架由程序维护。AI选择允许的模块种类及内容、位置和展示重点；不返回任意可执行 HTML、JavaScript 或 CSS。

首版模块：文字说明、分项建议、图文卡、指标卡、趋势图、安排列表、复盘总结。所有模块具有稳定 ID、页面、分区、类型、标题、内容或数据引用、排序、版本、来源、更新时间和适用日期。用户固定的模块不被普通整理自动移位。

允许操作：新增模块、更新指定模块、调整同分区顺序、隐藏已失效模块。移除页面模块不等于删除原记录或原图；历史仍可查。相同输入和相同内容不重复增加模块。

图表只能引用实际记录与程序计算的聚合，显示时间范围和数据不足状态，不允许模型编写测量点。指标卡与图表共用同一数据源，避免摘要与档案矛盾。

图文优先使用用户上传照片，保留来源、日期、描述和待核实状态。首版不依赖生成图片或外部配图服务；以后若加说明插画，应区别于用户真实照片。照片卡可立即进入待核实区，但不能直接代表实际摄入。

各页面共享业务对象引用，不分别复制一套“当前体重”“当前方案”。关闭记忆或删除来源后，后续模型上下文排除原文及其派生摘要；受影响模块标记待复核或按规则重新生成。

## 6. 饮食照片完整流程

### 上下文决定用途与是否入档（用户最新确认）

不能把上传照片、识别完成或核对食物名称等同于实际进食。AI综合本轮文字、关联照片、前后对话、进餐时间和既有记录，分别判断食物识别、事件性质、是否保存实际记录、是否影响方案。每次判断保留来源消息及目标餐次，不能把附近任意一句“吃了”关联到错误照片。

| 上下文 | 档案与摄入统计 | 方案和页面 |
|---|---|---|
| “这是我刚吃完的午饭”等明确本人实际进食 | 自动保存有来源的饮食记录；未知份量标明估算或待补充，不伪造精确摄入 | 更新已记录摄入，评估是否需要调整方案 |
| “准备吃这个”“这个能吃吗” | 不计实际摄入，不写成已发生饮食；保留对话中的候选分析 | 可显示餐前分析；结合目标判断是否更新下一餐建议或方案模块 |
| “菜单”“别人吃的”“只是拍一下”“没有吃” | 不进入本人实际饮食档案和摄入汇总 | 回答问题；仅在与本人方案确实相关时提出或应用有依据的页面更新 |
| 只有照片，无法由上下文判定 | 保存媒体及分析状态，不自动创建实际进食记录；必要时问是否已吃或准备吃 | 对话显示参考估算，不将估算直接放入今日已摄入 |
| 后续明确“刚才那份吃了半份” | 关联原照片并创建或修正同一餐记录，避免重复入档 | 重算有关视图并评估方案变化 |
| 后续纠正“没吃，那是给别人拍的” | 撤回错误的本人进食归属，排除原摄入并保留纠正历史 | 更新有关统计，复核受该记录影响的方案解释 |

默认明确上下文可自动入档，不要求每张照片都固定点击确认；继承用户逐次确认偏好。实际发生与营养估算可信程度分别保存：明确吃过可以记录事实，但不可读标签、模糊份量和模型推断不能变成已核验数值。识别结果修正不自动改变是否吃过的状态。

入档和改方案是两个独立决定：吃过一餐不必改方案；未吃过的餐前咨询也可能合理更新方案里的选择建议。日常餐图默认保存在对话或饮食时间轴，只有与长期方案有关时才加入方案页面，避免方案变成照片堆积。

以下“确认”包括上下文明确表达后的自动校验入档，或歧义时用户补充核对，不代表强制按钮步骤。本节最新规则优先于本文及旧交接中“所有食物照片必须逐次人工确认”的表述；检查报告等其他图片的核对规则不因此改变。

用户补充确认：原有拍照估算热量等饮食功能必须纳入本轮完整交付，不仅保存图片或提取食物名称。以下为必须实施的功能，而非后续可选项。

- 单餐识别：识别可见食物、饮料、烹饪方式和大致份量，支持多张照片属于同一餐，以及文字补充、餐前餐后照片与剩余量核对。多张图不能重复计算同一食物。
- 营养估算：展示单项及整餐热量范围，以及可估算的蛋白质、碳水化合物、脂肪范围；同时保留份量、用油、酱汁等估算依据和不确定项。无法可靠估计的项目显示未知，不强行凑数。
- 补充信息：优先利用包装营养标签、用户给出的重量和实际食用比例；不清楚时提出一个最影响结果的问题。允许修正食物、数量、单位、实际吃了几成和进餐时间，修正后重新计算，保留前次估算来源。
- 单餐图文卡：照片、食物明细、估算热量与营养、已吃/计划吃/未确认状态，以及结合当前方案的解释；既可从对话查看，也可在今日和档案定位同一餐。
- 每日汇总：只汇总已确认实际摄入，显示热量及营养范围、已记录餐次和记录完整性。缺少餐次时标明“已记录摄入”，不能当作全天总摄入；无记录不等于零摄入。
- 目标对照：仅在已有适用的个性化摄入目标且依据足够时展示目标对照或剩余范围，区分目标与实际估算；不默认给所有用户固定热量预算，也不把未记录的饮食当作可用额度。
- 后续联动：确认或纠正一餐后，重算当日汇总及有关图表，再触发方案评估；AI可更新下一餐建议、方案解释和看板重点。不得仅凭一次估算超出目标就生成惩罚性断食或运动安排。

营养数据保留食物、数量、单位、食用比例、估算范围、数据来源与模型/算法版本。模型识别和估算为候选，程序负责单位换算、食用比例及汇总校验。无法获得可信成分数据时保留粗估及不确定性，不伪称来自营养数据库。上下界汇总仅为估算边界，不表示统计置信区间。

上传照片及关联上下文 → 保存媒体并分析 → 判断本人已吃、准备吃、参考图片或未知 → 分别决定实际入档和方案更新 → 明确事实自动校验保存，歧义时追问 → 触发统一评估并更新有关页面。后续对话可以继续解析同一张照片的用途和食用状态。

识别过程结合与本餐有关的对话，不能把一张食物照片等同于全部吃完。重复确认不得产生两餐或两次方案修改。

事实保存与AI评估分开记录状态：分析或方案评估失败不丢失已确认记录，页面提示“记录已保存，方案评估待重试”。恢复后基于同一事件重试，不要求用户重传照片。外部图片发送沿用现有披露与同意流程。

## 7. 服务端与存储设计

保留 Python 服务、SQLite、记录校验、媒体管理、任务反馈、版本检查、备份恢复和启动脚本。重点拆分 product.py 中的编排以及前端整页拼接，避免继续添加关键词补丁。

处理顺序：接收输入并去重 → 读取版本化上下文 → 理解事实和更新意图 → 校验候选 → 构造变更集 → 按对象事务提交 → 返回真实回执与新状态 → 前端定位更新模块。

新增明确的数据对象：用户级访谈状态、页面模块、页面修订、评估任务、变更集。变更集包含触发事件、依据、修改理由、目标模块与基准版本、前后差异、执行状态和关联方案版本。来源 ID 由服务端绑定，模型不能自行伪造。

首阶段可在当前 SQLite documents 模式上扩展，保留现有逻辑对象；无需为页面重设计先做全量关系表改造。新增对象必须纳入导出、恢复、重置及迁移版本检查，不能只有在线显示支持。

照片确认等已独立提交的事件，通过持久评估任务衔接；任务状态为待处理、处理中、成功、失败待重试。每个触发事件与目标版本幂等关联，服务重启能恢复未完成任务。后台评估不得无限重试上游。

普通对话也要区分“事实已保存”“页面评估中”“页面已更新”“更新失败”。允许事实保存成功而生成失败，不能给出整体虚假的成功回执。对话请求返回时间与后台评估状态分离，前端可查询进度。

并发更新按模块/业务对象版本检测；过时模型结果不得覆盖新内容。重算时排除已执行动作。撤销按变更集处理；存在后续依赖时以纠正版本恢复，不回滚整份数据库。

首版不更换前端框架；拆分 API 客户端、页面渲染、共享模块渲染器和更新回执。模型传输适配器与业务协议分开，日后可独立比较模型。

## 8. 对现有规则的修订

- 替换“只有显式请求计划才允许返回plan”的门槛，改为每轮可提出有依据的页面/方案变更。
- 替换“计划只有1–8条事项”的页面表达；事项继续用于执行，方案页面另含文字、图文、图表与总结模块。
- 新会话不重置首次了解进度。
- 图片不再停在归档阶段，确认事件进入统一跟进流程。
- 旧设计“未经明确替换意图不更新执行计划”调整为：在用户开启自动跟进的默认流程中，AI可依据新的明确情况调整未来安排，显示变化、原因及生效范围；暂停状态和用户确认偏好保持有效。
- 保留不把目标当测量、图片候选需核对、事实来源可追踪、失败不伪报成功、历史不能被悄悄覆盖的约束。

## 9. 实施顺序

1. 完成页面模块与变更集协议，搭建今日、方案、档案渲染；将现有计划和档案映射为模块，迁移前隔离备份与验证。
2. 打通首次对话了解、档案增量整理、完整方案生成、更新回执跳转。此阶段就能在页面上看到真实变化。
3. 每日对话评估接入模块局部更新、临时安排与长期方案版本，完成不变、更新、澄清三类路径。
4. 图片确认接入持久评估任务，完成食物与份量核对、单餐热量及营养估算、每日汇总和目标对照、图文展示、复盘与趋势引用。
5. 以连续多天的虚构资料完成真实模型和浏览器验收，覆盖桌面、窄屏、刷新与重启；之后再进入用户实际使用验证。

前四项共同构成本轮完整产品范围，不能把第三、四项永久留为“后续优化”。先交付一条纵向可用流程，再扩展模块类型；运维只处理实际阻断。

## 10. 验收场景

| 输入/情况 | 必须观察到的结果 |
|---|---|
| 新用户逐轮介绍身体和生活情况 | 档案逐步成形，下一问题有针对性；刷新及新会话不重新访谈 |
| 资料不足但用户想先开始 | 展示有未知项的初步方案，不能宣称全面评估完成 |
| 完成初步了解并请求方案 | 方案页完整显示目标、饮食、活动等相关模块，不止聊天里一段建议 |
| “最近一直加班，原来的安排做不到”且没有“修改”字样 | AI评估是否更新；需要时方案与今日出现可见变化和原因 |
| 上传午餐照片，核对实际摄入 | 今日出现真实照片和记录，档案有来源，方案在有必要时更新 |
| 一餐多张照片，随后说明只吃了一半 | 不重复计算食物；食用比例更新后，单餐估算与每日汇总一致 |
| 上传包装营养标签或补充食物重量 | 使用可读标签及用户确认数量重新计算，显示估算依据；看不清的数值不编造 |
| 只记录午餐，没有早餐和晚餐 | 看板显示已记录摄入及缺失餐次，不宣称全天已吃够或剩余多少一定可吃 |
| 修改或删除一餐记录 | 单餐、每日汇总、趋势和受影响的解释同步更新，不残留旧的摄入数值 |
| 告诉系统“这张是菜单，没有吃” | 不计为摄入，不改变实际饮食统计 |
| 只上传照片且没有足够上下文 | 不自动入本人实际饮食档案或已摄入；参考估算与实际记录清楚区分 |
| “这是刚吃的午饭”并附图 | 默认按明确实际陈述自动入档，不强制再点确认；份量和营养不确定性保留 |
| 餐前咨询之后说“刚才那个吃了一半” | 正确关联原图和餐次，只产生一条实际记录；方案是否变化独立评估 |
| 仅新增说明文字或图片 | 页面版本变化，已存在任务及反馈保持不变 |
| 明天临时有事 | 仅相关日期变化，既往记录及后天安排不被误改 |
| 连续输入真实测量 | 图表使用原记录和真实日期；少量数据不生成虚构趋势 |
| 普通问答或重复输入 | 不凭空加卡片，不产生重复计划或记录 |
| 图片确认后模型超时、随后重试 | 已确认记录保留，评估状态可见，最终仅应用一次变更 |
| 撤销、两窗口并发或重启 | 变更可追踪，旧结果不覆盖新状态，待处理评估能够恢复 |
| 导出并在隔离环境恢复 | 模块、计划、档案、原图引用、修订与待处理状态完整 |

## 11. 模型判断与完成边界

目前代码中的更新门槛与缺失流程足以解释主要体验问题；尚未做同条件模型对比，不能下结论说模型能力足够或不足。先明确结构化协议和验收场景，再用相同虚构资料评估当前模型在访谈、图像、更新判断、模块内容和延迟上的实际表现。

本轮重设计完成不等于产品实施完成。最终交付以“聊完后页面按判断发生正确变化，记录与历史一致，持续多轮可用”为准，不能以测试数量、服务在线或回复篇幅代替。
