# 可选资料采集流程

> 2026-09-07 补充：用户认可首次对话按需采集资料的方向。下一轮应按用户当前问题选择相关表单，支持文字/语音混合回答，提交后继续原始计划请求。现有固定表单和浏览器语音入口的差距、目标与验收见 [产品重梳方案第 5 节](PRODUCT_REDESIGN_2026-09-07.md#5-四个页面重新分工)。以下保留当前实现说明。

## 1. 设计目标

当用户希望制定减脂或健康方案，而基础资料不足时，不在聊天回复中一次抛出长篇问题。系统提供两种平等入口：

1. **填写表单**：用户按意愿填写部分或全部资料；
2. **先不填，用文字/语音说**：立即返回聊天输入，用户只说愿意分享的内容。

表单不是强制门槛。用户跳过后仍可继续获得一般性帮助，模型后续一次最多追问一个对当前决定最有价值的问题。

## 2. 谁决定、谁展示

资料采集采用“模型判断 + 程序控制”的混合方案：

- 程序可根据明确意图和资料缺失情况直接触发，例如用户提出“帮我制定减脂方案”；
- 模型也可以在结构化响应中返回 `intake_form: true`，表示当前需要补充基本情况；
- 无论由谁触发，展示的都是前端代码中定义的固定表单，字段、校验、确认和落盘规则不由模型临时生成；
- 模型不得在自然语言回复中自行输出长问卷或 Markdown 表格。

这样既保留模型对上下文的判断能力，又保证隐私提示、字段范围和保存行为稳定可审计。

## 3. 触发条件

程序规则同时满足以下条件时触发：

- 用户表达减肥、减脂、瘦身、健康计划或制定方案等意图；
- `age`、`sex`、`height_cm`、`goals` 中至少一项尚未保存；
- 当前页面会话中没有选择“用文字/语音说”，也没有刚完成表单。

模型响应中的 `intake_form: true` 也可以触发同一表单。已有资料完整时，程序规则不主动重复展示。

## 4. 表单字段

所有字段均为选填：

| 字段 | 保存位置 | 校验 |
|---|---|---|
| 年龄 | `profile.json` 的 `age` | 1–120 |
| 身高 | `profile.json` 的 `height_cm` | 50–250 cm |
| 体重 | `records.json` 的 `weight` 记录 | 20–400 kg |
| 生理性别 | `profile.json` 的 `sex` | 最多 50 字符 |
| 目标 | `profile.json` 的 `goals` | 最多 500 字符 |
| 疾病或身体状况 | `profile.json` 的 `conditions` | 最多 20 项，每项 100 字符 |
| 过敏情况 | `profile.json` 的 `allergies` | 同上 |
| 正在使用的药物 | `profile.json` 的 `medications` | 同上 |

打开表单时会预填已有资料。空白字段不保存，也不会清空或覆盖原有资料。

## 5. 用户选择后的行为

### 填写表单

1. 用户填写任意一项；
2. 点击“确认保存并继续”；
3. 前端调用 `POST /api/intake`；
4. 后端在同一个锁范围内完成校验与保存；
5. 前端生成一条明确的“已确认资料”摘要，继续原话题；
6. 刚通过表单保存的数据不会再次生成候选确认卡。

如果没有填写任何字段，系统不提交，并提示用户填写至少一项或改用对话。

### 不填写

1. 用户点击“先不填，用文字/语音说”；
2. 当前会话标记为 `intake_mode: chat`，不再重复强制展示表单；
3. 输入框获得焦点，用户可以键入文字或点击语音输入；
4. 语音识别只负责填入文本，仍由用户确认后点击发送；
5. 模型接受部分信息，并且一次最多追问一个问题。

## 6. 隐私和安全约束

- 表单必须明确标注“全部选填”；
- 保存前必须由用户点击确认；
- 表单内容只发给本机 `/api/intake`，确认后才进入资料或档案；
- 后续健康对话可能把已确认资料的白名单字段作为模型背景；
- 紧急症状规则优先于资料采集，不得用表单延迟就医提示；
- 当前是可信本机单用户原型，资料仍以明文 JSON 保存。

## 7. 已知边界

- “本次选择不填”目前是页面内状态，刷新页面后不会保留；
- 程序关键词不覆盖所有表达，模型标记用于补充判断；
- 语音能力依赖浏览器支持和麦克风授权；
- 当前没有表单版本号、字段级撤销或完整资料变更历史。
