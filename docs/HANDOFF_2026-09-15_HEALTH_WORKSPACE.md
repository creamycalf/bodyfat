## 1. 用户确认的方向

产品是通过对话持续维护个人健康记录、计划和档案的助手。用户用“减肥的 Codex”帮助描述助手形态，但已明确纠正：计划和档案必须有独立菜单，可以从对话切过去查看。

用户反复指出的核心问题是显示与交互：大段说明、原始换行符和 Markdown 标记、重复版本及技术错误提示，造成页面难读，也看不出助手根据上下文更新了什么。

本轮确认的菜单与职责：

| 菜单 | 用户要看到的内容 |
| --- | --- |
| 对话 | 自然交流，提供文字、语音、照片，报告实际执行情况 |
| 看板 | 当前真实状态、体重趋势、今日饮食记录、今日安排和完成情况 |
| 计划 | 当前可执行安排、具体饮食选择、打卡、调整依据和历史版本 |
| 档案 | 助手已了解的身体情况、偏好、生活规律和健康背景，能查看来源并纠正 |

页面结构保持稳定，内容随上下文更新。用户希望能看到具体事项被调整，例如从晚间活动改到午休，而不是每次对话后追加一篇计划说明。

## 2. 本轮追加并确认的需求

1. 饮食具体到吃什么。自己做时给菜名、食材和做法；需要时点击获取详细做法。点外卖时给搭配、可在外卖软件搜索的关键词和点单备注。
2. 计划内可以直接打卡，也可以通过对话识别打卡；各页面使用同一份执行记录。
3. 可以查看历史计划、历史版本和对应打卡情况。
4. 用户认可本轮可点击样稿优于上一版，并要求先按这一版实施；后续继续结合实际页面讨论迭代。

## 3. 已实现并发布的内容

### 看板

- 由实际体重记录绘制曲线，展示最近记录值和变化。记录不足时显示空态。
- 展示今日饮食数量、营养估算范围，餐食详情可展开查看，已有原图可展示。
- 没有饮食记录时显示“未记录”，不将缺失记录当作零摄入。
- 今日任务和完成进度来自正式计划与打卡数据，提供对话记录入口。

### 计划

- 当前计划集中展示阶段目标、日期和执行事项，详细安排、制定依据及调整详情可展开。
- 饮食事项分成“自己做”和“点外卖”。新计划可保存结构化菜名、食材、步骤、搜索词及备注。
- 旧计划仍显示原有安排；缺少新结构时展示获取做法、获取外卖搜索建议的按钮。
- 点击获取会切到对话，携带准确的计划 ID、版本、事项 ID 和模式，结合档案生成说明。
- 已启用计划的今日事项支持完成、部分完成、跳过、延期、撤回反馈。
- 历史版本单独折叠，显示原计划与该版本打卡记录；历史版本不提供重新启用按钮。
- 最近调整先显示受影响事项，原始触发对话收起查看。

### 档案与聊天

- 档案按身体情况、目标与饮食偏好、生活规律、健康背景分组。
- 保留来源对话定位、手动编辑、待核实信息、实际记录、原图与执行反馈入口。
- 编辑表单支持清空已有字段。
- 聊天正文安全处理换行和加粗；补充页面模块收起，既有自动摘要不再重复铺在主页面。

## 4. 实现入口与数据约定

| 文件 | 作用 |
| --- | --- |
| `index.html` | 四菜单入口、页面标题、新样式加载 |
| `health-pages.js` | 看板、计划、档案渲染；饮食入口；打卡控件；历史记录 |
| `health-pages.css` | 正式版布局、卡片、饮食双列、手机适配 |
| `workbench-ui.js` | 计划正文、换行与加粗处理、调整说明、补充模块和照片显示 |
| `app.js` | API 调用、视图切换、打卡绑定、对话请求、档案编辑 |
| `archive-tools.js` | 图片核对与健康记录操作，原图及执行反馈折叠展示 |
| `product.py` | 计划规范化、饮食结构、只读做法请求、对话打卡处理 |
| `server.py` | HTTP 接口和新静态文件路由 |

饮食结构位于计划事项的 `meal_options`：

```json
{
  "cook": {"dish": "菜名", "ingredients": "食材", "steps": "分步做法"},
  "takeout": {"dish": "搭配", "search": "搜索词", "ordering": "点单备注"}
}
```

字段允许模型提供字符串或简单数组，保存时规范为有长度限制的文字。显示时转义，不执行模型提供的标记或代码。

做法请求在普通对话载荷中附加 `plan_help`，包含 `id`、`version`、`item_id`、`mode`（`cook` 或 `takeout`）。服务端查找真实事项，将其作为上下文，并忽略该次模型返回的健康事实、计划变更、页面变更和打卡写入。回答保留在对话中。

打卡仍使用已有键：`plan_id:version:item_id:date`。页面打卡与模型识别的对话反馈进入同一套反馈存储。对话反馈需具备本轮原话依据；新增对准备、未完成等明确表述的拒绝处理。

## 6. 当前限制与后续优先事项

### 本轮功能边界

- 现有用户计划在发布时为“待开始”。需要用户启用，才显示今日任务与打卡入口；发布没有替用户启用计划。
- 旧计划没有自动生成新饮食结构。获取做法的回复目前保存在对话里，没有自动回填成该事项的食谱卡片。
- 新计划的饮食结构仍依赖模型按约定返回；字段缺失时保留获取入口。
- 本轮上游回复使用隔离模拟验证流程，没有用用户健康资料重新验证真实模型的做法质量或复杂语义识别准确率。
- 目前只提供外卖搜索词和备注，不查询实时店铺、不代下单。
- 回复显示仍为真实处理阶段加完整正文返回，尚未实现上游正文逐字流式输出。

### 前次排查发现、不能视为本轮已修复的问题

- 饮食纠正涉及“朋友”等词时，现有事实过滤可能跳过纠正，使已有摄入记录保留；前次隔离探针已复现。
- 模型只截取“吃完了”作依据时，可能漏掉整句中的否定或纠正；前次隔离探针已复现。本轮打卡过滤不等同于修复饮食摄入判断。
- 页面更新失败的恢复入口目前依据已保存资料重建摘要，无法还原未持久保存的原始失败草稿。
- 计划修订会产生新版本和事项 ID，旧反馈仍保留，但未实现未变事项的当日完成状态自动继承。
- 上下文更新后，档案冲突可能进入待核实，计划却已根据新背景调整，需要继续检查两者一致性。

后续先根据用户对正式界面的反馈调整饮食信息密度和交互，再完善做法回填、具体餐次打卡及跨版本反馈衔接。涉及摄入纠正和事实一致性的既有问题应单独复现修复，不以页面验收通过替代数据正确性验收。

## 7. 后续开发与验收约束

- 正式后端是 `server.py`，`server.mjs` 仅用于 mock。
- 本地正式地址为 `http://127.0.0.1:8787/`。后台守护脚本为 `start-supervised.ps1`，本轮确认运行于隐藏 PowerShell 进程；不要假定存在同名计划任务。
- 合成健康数据只写临时隔离目录，不注入正式记录，不用真实用户照片作模拟测试。
- 调整界面保留用户真实资料、原图、计划与反馈；发布前备份，发布后核对数据。
- 不回退为只有聊天的界面，不将计划和档案变成只能从聊天打开的面板。
- 不因某一测试通过声称复杂模型理解已全部正确。交付时区分已实现、实际验证和仍待完善。
