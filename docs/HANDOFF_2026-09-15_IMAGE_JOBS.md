# 知衡图片分析与后台处理交接

日期：2026-09-15。最新实施补充，继承 HANDOFF_2026-09-14_WORKBENCH.md 和 PRODUCT_REDESIGN_2026-09-14.md。

## 已实现

- 图片上传支持 background=true：校验并保存原图后返回202和持久任务，不占用聊天窗口等待整轮模型请求。前端使用任务ID提交，重复ID返回同一个任务，不重复上传或创建记录。
- image_jobs.py 将任务放在现有 workspace.image_jobs 中，随SQLite、导出和备份保存。状态为 pending/running/succeeded/failed/partial；图片识别和后续对话为两个阶段。
- 后台图片识别成功后自动调用关联会话的业务处理，判断入档、摄入和页面变化。后续对话用稳定消息ID，重启接续依赖已有幂等回执，避免重复业务写入。
- 超时、网络连接错误、限流、上游故障和无效响应至多自动重试一次；鉴权错误不自动重试。失败可手动重试，重启恢复仍有尝试上限。人工重试明确重置尝试次数。
- 页面显示原图缩略图和任务阶段；刷新后仍可读取状态。模型返回页面/饮食校验问题或缺少工作台判断时显示partial，不把图片识别成功当成全部整理成功。
- 原图重新分析也支持后台处理。没有关联对话的历史原图重试只分析图片，不凭空补写用户食用意图。
- 抽出 server.analyze_image，prepare_only模式仅保存图片，不调用模型。标准化媒体路径保持隔离目录与备份兼容。
- 视觉结构化输出额度提升至至少4000；支持上游content文本块数组；截断响应明确返回AI_OUTPUT_TRUNCATED，不把不完整内容当成成功。
- 对已明确关联的食物图片，补充有原文依据的食用判断兼容：当前明确“还没吃”不入摄入；“刚才那个吃了一半”可在模型漏交动作或使用非约定状态时落地为实际记录。假设、他人情况、没有明确关联的普通进餐句不会走此补救。
- 半份/整份的明确表达可按图片已有参考营养换算；缺少参考数据或份量不明确时保留未知，不编造营养值。已有实际记录按同一图片更新，不新建重复餐次。
- 档案实际记录改成可读摘要，并修复长文本在390px页面溢出。

## 实际验证

- 84项Python回归通过，语音Node测试和前端语法检查通过。包含队列幂等、有限重试、重启接续、部分成功、鉴权失败、原图复用、明确食用比例和模型空占位字段。
- 隔离浏览器1280×900和390×844复验通过：四个页面无横向溢出、无脚本错误；刷新后任务状态仍显示。截图保存在tmp/workbench-v3-qa。
- 使用明确标记SYNTHETIC TEST MENU的虚构测试图，没有传输用户真实照片。简短识别标题约4.4秒成功；完整营养识别也成功读出每份600千卡、蛋白质20g、碳水100g、脂肪13g。
- 同一图片的真实对话复验：说“还没吃”时本人摄入记录为0；随后“刚才那个吃了一半”后保存恰好1条记录，300千卡、蛋白质10g、碳水50g、脂肪6.5g。最新测试已断言300千卡，不仅断言存在记录。
- 后台上传实测经历pending→running(image)→running(followup)→partial。图片分析成功，但后续模型漏交decision，因此如实标记partial；后续明确实际食用对话验证成功。这不是整轮自动页面更新无条件成功的证明。
- 上游本轮仍出现一次AI_INVALID_RESPONSE，前一轮存在约75秒超时。已证明当前配置能处理图片，但未定位上游波动的唯一原因；不能断言此前不支持视觉，也不能宣称延迟已稳定。
- 正式8787已由守护加载新版，任务Running、健康正常、image-jobs接口可读。切换前后正式逻辑文档SHA-256一致，测试没有写入正式健康资料。

## 后续仍需完成

1. 结构化页面判断仍可能漏字段；后台已区分部分完成，但尚未实现对页面生成失败的独立持久自动修复任务。不能把手动继续对话当成全自动页面恢复已完成。
2. 测试图是清晰标签文字，不等于自然餐食识别、份量估算或营养准确率验收；还需不同餐食、遮挡、剩余量等案例。
3. 首次了解的完整阶段/跳过/恢复状态机、一餐多图归并、个性化摄入目标及剩余额度仍未完整实现。
4. 模块排序/隐藏/固定/独立撤销界面仍未完整实现。历史原图没有关联上下文时，仍需用户在对话说明用途。
5. 服务仅限本机单用户，真实麦克风和用户日常流程认可仍需后续验证。
