# 知衡：持续营养管理 Agent 的产品决策与实施路线

日期：2026-09-23  
状态（2026-09-26 更新）：最新私人测试包为 0.4.20，增加配对模型对照与对话误改写修复。程序回归通过，对话自然度与真实输出质量仍未验收通过，P1–P3 尚未完整实施。最新结果与已知问题见 [0.4.20 交接](HANDOFF_2026-09-26_PHONE_TEST_0.4.20.md)。下文现状与根因保留决策时背景，不能当作当前缺陷清单。  
适用范围：当前独立 Android 私人测试应用。若本文与较早路线文档的“默认明天开始”等设计冲突，以本文为准；既有数据与安全校验不因改造而删除。

## 1. 结论

知衡下一步不应继续沿着“补齐问卷 → 生成完整食谱 → 固定每日打卡”的路线扩张。目标应是一个能在连续对话中完成**理解当下问题 → 核对必要事实 → 给出有依据且现实可行的下一步 → 观察执行与身体反馈 → 局部修订方案**的营养管理助手。

它可以帮助用户理解营养和体重管理、整理体检信息、比较真实可获得的餐食、形成与修订行为方案；不能自称持证营养师、独立诊断疾病、决定检查或药物治疗，也不能把模型生成内容当成已验证的临床判断。所谓“专业”，首先是证据、边界和执行反馈可追溯，不是回复更长、数字更精确或菜谱更多。

本轮手机体验提出的四个验收问题，优先级高于新增页面或更换模型：

1. 不再反复问“明天吃什么”，不向用户解释内部“开始节点”。
2. 建议说清依据、未知和何时值得与专业人员讨论检查，不止于“少吃饭”。
3. 按手机当地时间和用户实际已吃/未吃的餐次处理今天；外卖推荐必须受真实菜单与可得性约束。
4. 通过持续复盘修订方案，而不是不断生成一份新的通用计划。

## 2. 已核实的现状与根因

| 用户观察 | 代码中已核实的原因 | 需要改变的产品行为 |
| --- | --- | --- |
| 总被带向“明天开始” | `intake.py:timing_contract` 明确规定首次完整计划默认明天；`product.py` 约第 1100 行还会在无日期时追加“明天开始” | 日期不再是普通咨询的门槛。只在真正安排周期行动时确定生效日期；默认考虑今天剩余时段 |
| 计划后反复要求下次起床、早餐前汇报 | `product.py` 约第 1123、1174 行创建固定 `start_guide` 并覆盖自然回复；Android `app.js` 约第 66 行固定显示前两项 | 下一次反馈由当前行动、已知记录和用户作息决定；已报告过的不再问，允许“不记录” |
| 建议浅、像模板 | 当前长提示词同时承担自然回答、抽取事实、生成计划、页面与打卡；回复还有 150 字上限。营养数值目前缺可靠数据库，代码因此限制精确营养处方 | 不用更长提示词掩盖资料和工具缺口。先拆清“回答、判断、行动、保存”的职责，建立依据链 |
| 出现“清蒸鲤鱼”式不现实推荐 | `product.py` 要求每个饮食事项同时生成自做和外卖选项；外卖仅有菜名、搜索词、点单备注。当前 Android Manifest 没有定位权限，也没有实时商家/菜单接口 | 候选菜必须先符合用户的购买/做饭条件。没有真实菜单时只给可搜索的类别或请用户提供菜单，不编造附近店铺与库存 |

`product.py` 已把本机 `date`、`local_datetime` 送入模型，也有当天已过餐次的排除逻辑；因此问题不是“完全没有时间”，而是默认次日规则压过了对话情境。当前时间没有显式时区来源字段；网页版若部署在异地服务器，还需避免把服务器时间误当用户当地时间。“开始节点”并非源码中的固定文案；无论它来自模型解释还是页面措辞，都不该成为用户理解建议的前提。

已有的请求分流、事实来源/更正历史、摘要确认、危险方案阻止、事实保存与模型失败分离是有用底座，应保留。`0.4.10` 私人测试 APK 已修复模型接口地址；它证明接口可用，不证明长期咨询质量、真实餐食识别准确度或临床有效性。当前 219 项 Python 回归主要验证状态与流程，不可作为专业建议质量的证据。详见 `HANDOFF_2026-09-23_CONSULTATION_MEMORY_PHASE1.md` 和 `HANDOFF_2026-09-23_PHONE_TEST_0.4.10.md`。

## 3. 一轮对话应如何工作

先判断用户**此刻要做什么**，再决定是否需要查资料、追问、调整计划或保存事实。普通问答、当下选餐、实际进食记录、体检指标解读、正式个体方案、执行复盘、高风险症状要分流。不得把所有问题转成建档或计划请求。

最小对话契约：

1. **先回应本轮问题。** 即使资料不足以制定完整方案，也应给出当前证据范围内有帮助的解释或下一步；不得用“请先完成评估”覆盖整段回答。
2. **仅在答案会改变下一步时追问。** 优先一个问题，并解释用途；已确认、明确拒答或最近刚回答的内容不重复问。用户随时可回到原主线。
3. **分级表达建议。** 通用科普、可逆的单餐选择、阶段性行为试行、需要临床评估的事项所需资料与权限不同。一个缺项只限制依赖该信息的判断，不阻断全部帮助。
4. **区分事实与推断。** 用户原话、体检报告原文、食品标签/数据库、模型估计、待确认信息分别存储；计划不是实际摄入，漏记不是未进食。
5. **每轮说清实际完成了什么。** 聊天答复、事实入档、计划版本更新、餐食记录、外部查询分别给回执；失败不能声称已保存。

对于“我 200 斤，想减到 150 斤”，合格的首轮回应不应直接给精确热量和七天食谱，也不该连续问几十项。它应承认这是长期目标，说明仅凭体重无法判断目标和方式是否适合；先问一项会改变判断的关键信息（例如身高或当前已知健康限制），并给用户一个无需等待完整建档就能开始的、低风险且可按现实条件调整的观察/选择动作。后续根据回答逐步增加个体化程度。

## 4. 时间、位置与“现在能吃什么”

**时间决策由程序负责，模型负责解释。** 保存本机时间、时区、对话发生时间、用户自述作息与今天餐次状态；不凭固定钟点猜轮班用户何时吃饭。

| 情况 | 期望行为 |
| --- | --- |
| 用户问“现在/今天吃什么” | 立刻讨论下一次可实际选择的餐，不要求先生成七天计划，也不自动切到明天 |
| 用户要开始阶段方案，今天还有可执行时段 | 今天仅安排剩余时段的一项可行行动；已过餐次不补吃、不以节食补偿 |
| 今天已无合适执行机会 | 今天仍给准备或判断上的帮助；首个定时行动可从明天开始，并说明是因为时段已过，不是内部规则 |
| 用户明确指定日期或轮班生活节点 | 尊重指定日期/起床、上班、下班等生活锚点；冲突时澄清，不改写用户意图 |

**位置按最小必要原则使用。** 第一层让用户自愿设置城市/区县或常用商圈；第二层让用户发送正在看的外卖店链接、菜单文字或截图，由程序/模型比较真实候选。只有在明确选择服务商、接口许可、费用和隐私方案后，才接入实时商家数据。精确 GPS 不应是营养咨询的默认权限；没有商家数据时，界面必须标明“搜索建议”而非“附近可买”。菜单查询结果需保留来源与查询时间，餐品、价格、营业和库存可能变化。

推荐优先回答“这家店现在有的几样里怎么选、怎样点、吃不下/没有货怎么替换”，而不是构造一份理想化菜单。过敏、禁忌、预算、路程、做饭能力、口味和份量不确定性都应进入比较；不能仅凭菜名推断真实用油、酱料或营养数值。

## 5. 专业建议的证据契约

每条影响健康决策的建议至少要能追溯：

`建议/行动 → 引用的用户已确认事实或检查指标 → 可核对的指南/数据来源 → 未知或假设 → 何时复盘/升级处理`

界面不必把每次聊天写成论文，但应能展开“为什么这样建议”。如果依据只是模型估计，应明确写“估计”，不能伪造文献或把未知值填成零。指南要记录名称、版本/发布日期、适用人群和原链接；临床内容上线前需要有资质人员审阅，版本更新后复核。

“建议做检查”应设计为**带触发条件的就医讨论建议**，不是模型自动开单。例如，若用户已有较高体重且缺少近期健康评估，可建议在常规就诊时与医生核对血压、血糖/HbA1c、血脂等既往结果及是否需要补查；如果已提供结果，就针对异常项、时间和背景解释下一步，而不是重复要求检查。仅凭“200 斤”不能确定个人应做的全部项目，特殊症状、疾病、用药和年龄会改变判断；不能把所有人都导向昂贵的体脂/激素/影像检查。中国国家卫健委[《肥胖症诊疗指南（2024 年版）》](https://www.gov.cn/zhengce/zhengceku/202410/P020241020715873679737.pdf)可作为本地临床框架；[NIDDK 对安全体重管理项目的说明](https://www.niddk.nih.gov/health-information/weight-management/choosing-a-safe-successful-weight-loss-program)强调个人条件、持续支持与反馈。产品引用这些资料不等于获得诊疗资质。

高风险症状、进食障碍线索、孕哺期、未成年人、复杂疾病或用药情形应进入更保守的分流：先给恰当的就医/急诊建议和问题整理，不生成激进减重目标、不自行调整药物。安全规则、过敏冲突校验与错误恢复不能因改善话术被移除。

## 6. 技术切分：先做一个可靠的 Agent，不急于多 Agent

保持现有本地存储与 Android 底座，逐步从 `product.py` 的大编排中抽出职责：

| 能力 | 责任边界 |
| --- | --- |
| 对话路由 | 判断本轮是科普、选餐、记录、方案、复盘或高风险；允许一个话题临时打断另一个 |
| 事实与记忆 | 保存原话、人物归属、时间、来源、确认/撤回/过期状态；跨会话恢复，避免重复问 |
| 评估与证据 | 明确当前主要问题、支持它的记录、反证/未知、允许作出的判断 |
| 行动与计划 | 先产生 1–2 项可执行行动；保留计划版本、适用日期、替代项和反馈条件；修改尽量局部化 |
| 受控工具 | 本地时间/时区、用户授权的位置、真实菜单、食物数据库、版本化指南；工具失败透明降级 |
| 安全与保存 | 程序校验日期、单位、数值、来源、过敏和危险建议；模型不得直接宣布持久化成功 |
| 追踪与评估 | 留下可脱敏的“输入—路由—工具—判断—输出—保存结果”轨迹，用场景集发现反复追问与幻觉 |

模型负责理解、比较候选与自然解释；程序负责持久状态、日期运算、营养计算、来源校验和安全门槛。Skill 值得借鉴的是任务边界、按需加载知识和工具契约，不应把第三方 Skill 文本直接粘成一个更大的系统提示词。[OpenAI 的 Agent 定义](https://developers.openai.com/api/docs/guides/agents/define-agents)与[工作流评估指南](https://developers.openai.com/api/docs/guides/agent-evals)可作工程参考；是否采用某个 SDK、多 Agent 或新的云服务，须由本项目的评测、延迟、费用和数据边界决定。

## 7. 实施优先级与完成条件

### P0：修手机上的错误体验（先交一版可测试 APK）

- 删除“首次完整计划默认明天”的隐式强制；保留用户明确指定日期的能力。
- 取消生成后覆盖自然回复的固定起床/早餐话术；`start_guide` 改为基于当前行动与尚未反馈事项的可选引导，不把它暴露为必经步骤。
- 降低“每个饮食事项同时必须有自做+外卖”的要求：只有资料足够且现实可行时展示相应选项；没有真实菜单时不生成具体店铺、价格、库存或“附近推荐”。
- 用隔离的合成场景加真实模型人工审阅覆盖：晚上问现在吃什么、已吃早餐、只想问一餐、轮班作息、用户说不想做鱼、计划进行到第三天。保留原有安全与幂等回归。

完成标志：这些场景不再无故切到明天、不重复问已知事实、不要求补做已过餐次；模型失败时已有事实与原话不丢。完成后按 `AGENTS.md` 的私人测试包规则打包并真机验证。测试通过只代表本阶段体验，不宣称临床有效。

### P1：有依据的建议与检查沟通

- 设计可展开的依据卡：用户事实 ID、指南/食品数据来源、未知项、建议强度、适用条件、复盘点。
- 加入经审核的中国肥胖/食养与相关慢病资料索引；先做少量高频场景，不做无边界的医学联网搜索。
- 检查建议按风险线索触发，并清楚区分“已有报告解释”“常规就诊讨论”“需及时就医”。
- 建立“不迎合用户”的评测：目标不合理、想快速减重、要求停药、把体重波动解释为失败时，能礼貌指出证据不足或风险。

完成标志：抽样建议均能追溯依据；没有证据时能承认未知；临床内容经过专业审阅；危险情形不生成治疗处方。

### P2：真实可买的选餐助手

- 先支持菜单文字/截图/链接的候选抽取与用户核对，显示商家/菜品数据来源及时间。
- 用偏好、禁忌、预算、可得性、份量不确定性排序；提供 1–2 个主选和一个现实替代，说明点单修改点。
- 若仍需实时附近商家，再单独决定定位权限、商家数据供应商、费用、许可、隐私和断网降级；不要把通用网页搜索误称为实时库存。

完成标志：从用户给出的三家真实菜单中能选择可下单的方案；遇到缺货或用户不吃某食材可局部替换；无数据时不编造商家。

### P3：长期修订，而非每天重做计划

- 记录行动是否尝试、饥饿/饱腹、睡眠、执行阻碍、体重趋势和记录覆盖率；“未记录”单列。
- 约定复盘触发条件，结果为保持、减小难度、替换、补充观察或建议专业支持；保留旧版本和修改原因。
- 用多周对话测试跨天恢复、纠错、遗漏、出差与临时聚餐；不以一次体重变化惩罚式收紧计划。

完成标志：用户说“这两周很饿、没坚持住”时，系统先分析现有证据和困难，只改相关行动，并说明依据与下一次观察条件。

## 8. 评测与发布门槛

先建立可重复的**连续生活场景集**，而不是只数单元测试。至少包含：

- `200 斤 → 150 斤`，信息不足但需要立即有帮助的回应；
- 当地晚间、今日已吃两餐，问“现在点什么”；
- 用户已说早餐，下一轮继续谈减重；
- 用户拒绝提供一个字段，后来又主动补充；
- 用户给出体检指标或说“这是我爸的报告”；
- 外卖菜单中无模型首选、含过敏原或营业状态未知；
- 连续两周反馈饥饿/执行困难、漏记、体重单日波动；
- 模型超时或结构化整理失败后重试。

每个场景分别评分：是否先回答当前需求、是否重复追问、事实归属和时间是否正确、依据是否真实、建议是否可获得且可执行、安全边界、是否正确保存/不保存、后续是否按反馈修订。真实模型评测与 Android 真机体验都需要；合成服务下的功能测试不能替代。涉及健康资料的日志与评测样本应脱敏并与生产 `.data` 隔离。

发布私人测试包时仍遵循根目录 `AGENTS.md`：默认内置模型配置，只从受控环境读取密钥，校验 APK 版本、签名、内置地址与 SHA-256，保留旧包，不打包真实健康资料。当前明文 HTTP 模型服务和 APK 内嵌密钥只适合本人测试，不能当作公开分发架构。

## 9. 参考项目的借鉴边界

- [ask-guzhongyi](https://github.com/guzhong1/ask-guzhongyi)：借鉴先回答、少量关键追问、抓主要矛盾与医疗边界；不复制受非商业授权限制的内容或真人身份。
- [Waistline](https://github.com/davidhealey/waistline)、[wger](https://github.com/wger-project/wger)：借鉴食物来源、记录、计划和备份的结构；代码许可需单独评估，不直接移植。
