# 知衡营养师化改造实施方案

日期：2026-09-21  
目标：把当前“固定字段问卷 + 模型生成计划”改成“评估问题 + 共同制定行动 + 持续复盘”的营养管理流程。

## 一、改造目标

用户完成一次对话后，应能感受到系统做了四件事：

1. 听懂用户当前最想解决的问题，而不是只收集资料。
2. 根据问题选择最有价值的追问，并解释为什么问。
3. 给出少量、具体、符合生活条件的第一阶段行动，而不是未经核实的完整处方。
4. 约定下一次反馈，并根据真实执行情况调整方案。

本次不把“问完全部字段”作为生成方案的前置条件，也不以回复长度、问题数量或测试数量作为专业度指标。

## 二、现状问题

### 1. 追问控制权仍在固定字段推进器

`intake.py` 的 `QUESTIONS` 和 `missing()` 按固定顺序找缺项，`product.py` 在建档分支里又强制取 `gaps[0]`。模型提示词要求动态追问，但程序最终会覆盖模型选择。

结果是：用户刚说出一个重要困难，系统可能继续问年龄、性别或其他未填字段；用户只想记录一餐时，也可能被带进完整建档。

### 2. 没有持久化“当前评估判断”

当前有 profile、records 和 assessment 摘要，但没有清晰保存：当前主要问题、证据、未知点、优先级、允许采取的行动、下一次复盘条件。

### 3. 方案生成和事实保存耦合太重

同一轮同时处理档案、记录、方案和页面。模型计划不合格时，用户很难知道哪些资料已经保存，下一次也容易重复提交。

### 4. 方案缺少行动和反馈闭环

已有 `start_guide` 和任务反馈，但仍偏固定清单，未把每个行动和问题依据、替代方式、反馈指标、复盘日期关联起来。

### 5. 模型仍可能产生看似专业但无依据的数字

当前提示词已经限制了克数和热量，但真实模型仍出现过把“一碗”改成具体克数、生成精确热量等情况。提示词不能代替程序验证和可靠数据源。

## 三、目标业务流程

### 阶段 A：理解目标

首次或新主题对话先确认：

- 这次最想改善什么；
- 什么时候最困扰；
- 过去尝试过什么，为什么没有坚持；
- 当前是否存在需要先澄清的健康风险。

如果用户明确只想记餐或问一个问题，不强制进入完整访谈。

### 阶段 B：定向评估

根据当前主题选择一个优先问题，每轮只问一个主题。示例：

- 减重困难：典型一天饮食、加餐、饥饿、过去减重经历、活动和睡眠。
- 晚餐不适：相关餐次、发生时间、症状、份量、手术与用药情况。
- 计划难执行：上班/上学、通勤、做饭条件、预算和最常失败的时段。

模型提出问题后，程序检查是否与当前评估缺口匹配；不再简单取固定字段列表的第一项。

### 阶段 C：阶段总结

每完成一个小主题，向用户展示：

- 我目前了解的事实；
- 仍不能确定的地方；
- 我认为最值得先处理的一个问题；
- 用户可以纠正、补充或跳过。

总结不能把模型判断写进 profile 作为用户事实。

### 阶段 D：第一阶段行动

资料足够支持一个安全的行为建议时，不必等待所有档案字段齐全。每次先给 1～2 个行动，每个行动包含：

- `problem`：针对的问题；
- `basis_record_ids`：依据的事实记录；
- `action`：用户具体做什么；
- `when`：相对生活节点或用户已确认时间；
- `minimum`：最低可执行版本；
- `alternatives`：外食、加班或不方便时的替代；
- `feedback`：需要反馈的感受或行为；
- `review_at`：何时复盘；
- `unknowns`：仍未确认的限制。

没有可靠数据时使用熟悉的份量和范围，不生成精确热量处方。

### 阶段 E：执行与复盘

每日只问与当前行动有关的反馈。记录计划、实际完成、部分完成、未完成和未记录，不能混为一类。

复盘时根据执行难度、饥饿感、症状、记录覆盖率和趋势决定：保持、降低难度、替换行动、补充评估或建议寻求专业帮助。单日体重变化不能自动收紧计划。

## 四、数据结构改造

保留现有 SQLite JSON 文档，不迁移正式数据。新增或扩展以下对象。

### `assessment_state`

```json
{
  "stage": "understanding|assessment|trial|review|follow_up",
  "topic": "晚餐后不适",
  "primary_problem": "用户明确描述的问题",
  "evidence_record_ids": [],
  "unknowns": [],
  "priority": "high|medium|low",
  "next_question": {"topic": "meal_symptom", "reason": "需要判断是否与晚餐相关"},
  "user_summary": "给用户看的阶段总结",
  "updated_at": ""
}
```

### `assessment_history`

保存每次评估的版本、依据、结论和失效原因，避免新一轮模型重写历史判断。

### `plan.actions`

计划从纯文本事项扩展为行动对象。旧计划读取时保持兼容，缺少新字段的旧事项显示为“旧版计划行动”。

### 事实状态

每条 profile 和 record 继续保留原始证据，并增加或统一：`status=confirmed|pending|inferred|corrected`、`source_message_id`、`observed_at`、`valid_until`。模型推测永远不能直接成为 `confirmed`。

## 五、代码改造顺序

### P0：保存和状态可信

- 抽出 `apply_facts()`、`save_assessment()`、`save_plan()` 的独立事务边界。
- 结果回执分别报告：档案已保存、餐食已保存、评估已更新、计划是否保存。
- 计划拒绝或模型超时时，已确认事实仍然可读，重试只重试未完成阶段。
- 把照片上传、识别、用户确认、实际饮食记录四种状态分开。

### P1：动态评估状态机

- 新增主题和目标识别；允许当前问题覆盖固定字段顺序。
- 由程序根据主题、已有证据和安全限制生成可问主题集合。
- 模型只能在可问集合中选择一个问题，并返回 `question_reason`。
- 继续支持用户跳过、只记录一餐、先要初步建议和稍后继续。
- 旧字段继续保存，旧的固定 `missing()` 只作为档案完整度展示和兜底，不再决定唯一追问。

### P2：依据驱动的阶段方案

- 计划校验要求行动有问题或目标、有来源证据、反馈方式和复盘日期。
- 删除无法追溯来源的精准热量、消耗和份量结论。
- 将餐次、睡眠、工作和轮班时间转换为生活节点；用户没有提供钟点时不得编造钟点。
- 计划页显示“为什么先做这两件事”和“做不到时怎么办”。

### P3：连续跟进和周复盘

- 今日页显示当前行动、实际记录、下一步和待反馈项。
- 支持常吃餐复用、临时替代和同一餐修正，避免重复累计。
- 按约定日期生成复盘卡，复盘结果产生新的评估版本和计划版本。
- 连续多日未记录时显示恢复入口，不显示失败或责备文案。

### P4：真机和专业内容验证

- 安卓真机验证相机启动、回传、压缩、进程恢复和失败重试。
- 使用多种中文表达做连续 7 天模拟测试。
- 由营养专业人员或有经验的审核者抽查行动依据、食物份量表达和风险边界。
- 将模型实测原文纳入回归样本，防止只测 JSON 格式而不测建议质量。

## 六、验收场景

1. 用户晚上首次使用，只说“最近晚餐后不舒服，想减肥”：系统先围绕症状和晚餐追问，不直接生成完整减重计划。
2. 用户只说“今天午饭吃了面条”：保存午餐事实并追问必要份量，不强制完整建档，不把面条扩展成其他餐。
3. 用户说“明天上班很忙”：方案改为明天的可执行替代，不重写长期计划。
4. 用户回答年龄后模型失败：年龄在档案中仍可读，计划失败原因单独展示。
5. 用户说“昨天没做到”：行动状态为未完成并询问阻碍，不生成补偿性节食或运动。
6. 用户上传照片但未说是否吃过：保存图片分析状态，不写入已摄入；后续说“只吃了一半”时修正同一餐。
7. 用户提供轮班作息：使用起床、上班、下班和睡前等节点，不硬编码早餐 8 点、午餐 12 点。
8. 一周后记录不完整：明确证据不足，只基于已知内容复盘，不把未记录当作未执行。

## 七、发布策略

不立即替换全部旧流程。先在临时数据目录完成 P0/P1 回归，再用真实模型进行连续 7 天模拟；通过后生成新 APK。正式数据不使用合成测试数据覆盖，旧版计划和档案保持可读。

## 八、完成标准

达到以下条件才认为“营养师化第一阶段完成”：

- 新主题不再固定从年龄开始问；
- 每个追问有可见理由，并且不会重复已确认事实；
- 阶段行动能指出问题、依据、替代和反馈；
- 模型失败不会丢失已经保存的事实；
- 方案中的关键数字都能说明来源或明确标为估算；
- 连续 7 天模拟中，系统能根据反馈调整，而不是每天重新生成一份计划；
- 真机照片流程有成功、失败和恢复结果。

## 九、明确不做的事情

- 不直接照搬 Luma、wger 或其他项目的整套后端；
- 不因为“专业感”增加更多长问卷；
- 不把模型写得更长当成专业能力；
- 不在没有数据依据时增加精准热量、基础代谢或运动消耗数字；
- 不把公开项目的 README 宣传内容当成临床有效性证明。
