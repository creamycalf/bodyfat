# 知衡需求重梳与产品改造方案

日期：2026-09-07。状态：核心链路已实施，完整设计仍有待完善项，实际交付与验收以 [IMPLEMENTATION_V2.md](IMPLEMENTATION_V2.md) 为准。依据：用户明确要求对话生成对应计划、档案，并在看板和档案页看得到。

本文作为下一轮产品改造基线。与旧需求有冲突的地方在文中明确标出；现有系统尚不具备本文描述的新能力。

## 1. 产品目标与完成定义

知衡是一套以对话为主要入口的个人健康管理系统。用户用自然语言描述自己、提出目标、请求计划、汇报执行，系统负责整理和持久保存，让用户在看板知道下一步做什么，在档案知道系统记住了什么。

一条对话的处理结果可以包含多个业务动作，而不只是一个回复。只有数据保存成功、相应页面可读、刷新或重新打开后仍然存在，才算完成“生成计划”“建立档案”“记录完成”。

核心闭环：理解对话 → 区分事实和意图 → 更新档案/生成计划/记录反馈 → 展示处理回执 → 同步看板和档案 → 后续对话引用并调整。

## 2. 当前差距与根因

| 用户预期 | 当前实现证据 | 根因及需要补齐的能力 |
|---|---|---|
| 让我生成计划，看板就有计划 | `server.py` 没有计划实体、计划存储或计划接口；聊天仅返回 reply/extracted_data 等 | 将计划从一段回复提升为可保存、有版本的业务对象 |
| 说出年龄、身高、习惯后能形成个人档案 | 聊天结构化输出没有 profile_patch；个人资料主要由 `/api/profile`、`/api/intake` 写入 | 建立自然语言资料提取、合并、纠错和来源追踪 |
| 看板显示为我制定的安排 | `dashboard()` 读取 records，`today_recommendation()` 主要按近期睡眠返回固定分支 | 看板读取当前计划、今日安排和真实执行记录 |
| 档案里看得到“我是谁、什么情况” | 前端长期资料编辑在“我的”，档案主要呈现事件 | 档案升级为个人健康信息中心 |
| 说“今天做完了”会更新计划进度 | 无任务实例、执行事件、任务匹配机制 | 把实际反馈关联到具体计划项及日期 |
| 说“改成明天”是在调整原计划 | 无计划身份和版本，记忆只有 profile 与检索命中的 records | 明确调整目标、影响范围，保留旧版本 |
| 系统说保存了就真的保存了 | 聊天和历史保存是前端分开的请求 | 服务端统一处理并返回真实写入回执，避免只说不做 |

已有超时控制、备份和测试是可复用基础，但当前 30 项测试没有覆盖上述产品闭环，不能作为新需求的完成证据。

## 3. 六类信息必须分开

| 对象 | 示例 | 展示位置 | 关键约束 |
|---|---|---|---|
| 个人档案 | 年龄、身高、工作、外卖偏好、手术史 | 档案总览与分类详情 | 描述相对长期背景，保存来源与更新时间 |
| 健康记录 | 今天测得体重、昨晚睡眠、某次进食 | 档案时间轴、看板指标 | 描述实际发生的事件，区分发生时间和录入时间 |
| 目标 | 想改善作息、希望达到的体重 | 看板计划摘要、档案目标 | 目标值不等于测量值；未提供期限时不得虚构 |
| 计划及计划项 | 本周安排、可执行步骤、复盘条件 | 看板当前计划、完整计划详情 | 有 ID、版本、状态、适用期限、依据 |
| 执行反馈 | 完成、部分完成、跳过、延期及原因 | 看板今日事项、档案执行时间轴 | 关联计划项和具体日期；没反馈不算没完成 |
| 待核实信息 | “可能尿酸高”、识别不清的报告 | 对话核实卡、档案待核实区 | 不能作为已确诊疾病或已发生事实使用 |

对话历史保存原话和系统回执，是上述对象的来源，不替代上述对象本身。

必须区分：当前体重/目标体重、准备做/已经做、我的情况/家人的情况、确定事实/假设问题、过去事件/今天事件、用户陈述/模型推断。

## 4. 保存与确认策略

用户要求自动形成计划和档案。建议默认采用“明确陈述自动整理保存，存在歧义时核实，所有变更可见且可撤销”的方式。

这与旧文档“全部 AI 提取都必须二次确认”不同，是本轮提出的产品策略调整；实施时应统一相关文档、界面说明和测试。

下列输入为虚构交互示例，不代表任何人的实际健康资料。

| 输入或变化 | 默认处理 |
|---|---|
| “我38岁，身高175厘米” | 明确本人陈述，校验后保存资料，回执展示字段和撤销入口 |
| “今天体重99.8公斤” | 自动保存实际测量事件；看板与档案同步更新 |
| “我做过某项手术” | 核对具体手术后保存为用户自述，不能标成医疗机构核验结论 |
| “我可能尿酸高” | 存为待核实线索；不能写入确诊疾病 |
| “如果我只有80公斤呢”或“我爸80公斤” | 用于本次讨论，不更新本人测量值 |
| 图片/OCR 提取数值 | 待用户核对后保存正式记录；保留来源和修正值 |
| “帮我制定一个计划” | 生成并保存建议计划，看板立即显示；不要求复制粘贴或再次手动建计划 |
| “就按这个执行”或“从今天开始” | 激活指定计划，生成对应日期的执行事项 |
| “帮我制定从今天开始执行的计划” | 明确包含执行意图，生成后直接激活，并给出撤销/调整入口 |
| “今天的任务做完了”但今天有多项任务 | 追问指哪一项；不能批量标记完成 |
| 与旧资料冲突且无法判断是纠错还是新事件 | 展示原值、新值和来源，请用户核实 |
| “刚才说错了，是98公斤” | 精确关联到上条测量的纠错，保留修改历史；关联不明确则先问 |

提供“每次确认后保存”的可选偏好。首次使用清楚说明自动整理和撤销机制，不能用隐藏设置制造自动保存。删除、覆盖整份档案等继续明确确认。

建议计划与执行中计划都必须可见。若已经有执行中计划，新生成的替代建议不能偷偷替换它；展示差异，按用户明确的替换意图决定是否启用。

## 5. 四个页面重新分工

### 首次使用补充：围绕当前问题了解用户

用户补充确认：现有首次对话提供资料采集入口的方向保留。新用户尚无基本资料时，针对用户提出的问题提供表单式提问，也支持文字与语音回答。不能将所有首次对话都变成同一份全量问卷。

| 当前问题 | 首轮可选表单内容示例 | 不应发生的行为 |
|---|---|---|
| 希望制定减脂计划 | 当前身高体重、目标、日常饮食与活动约束、相关健康背景 | 无条件要求填写与此次计划无关的全部资料 |
| 希望改善睡眠 | 常见入睡/起床时间、持续多久、夜醒、白天状态、作息约束 | 先强制填写减脂表单 |
| 希望调整外卖饮食 | 饮食目标、常见选择、过敏/忌口、预算或选择范围 | 已明确的信息再次要求填写 |
| 单纯记录一次体重 | 数值、单位、实际测量时间，仅补缺失项 | 先完成完整访谈才能记录 |
| 一般知识问题 | 直接回答，需要个性化时再询问 | 默认建立个人健康档案或生成计划 |

表单根据意图、已有档案和本轮已说的信息选取少量相关字段，已知项预填、未知项可跳过。字段来自程序维护的白名单和模板；模型选择需要询问的字段及理由，不能任意创建网页或绕过校验。

表单提交后，系统必须继续用户最初的问题，例如完成原先请求的计划，而不能仅回复“资料已保存”。原始目标、已回答项、跳过项和当前追问状态需要持久保存，避免刷新后重新问一遍。表单、文字和语音可在同一轮采集中混用，并合并到同一份档案。

### 语音输入是首版必需能力

现有代码已经有浏览器 `SpeechRecognition/webkitSpeechRecognition` 的中文识别入口：识别结果填入输入框，由用户发送。但目前没有独立音频转写后端，不支持该能力的浏览器只有提示；现有识别结果还会直接覆盖输入框原文。该实现不能视为语音能力已完整验收。

目标流程：开始录音 → 展示正在收音及停止/取消 → 转为可编辑文本 → 用户核对发送 → 与键盘输入走相同的资料提取、表单补充、计划生成和反馈保存流程。

- 支持中文口述基本资料、回答追问、描述饮食/睡眠，以及汇报计划执行。
- 识别开始时保留原有草稿；取消、失败、重复回调不能覆盖已有文本或重复发送。
- 表单采集时允许“语音回答”，提取结果预填对应字段供核对；不要求每个字段单独说一遍。
- 对体重、身高、时间、单位及药名等转写结果可核对、可修改；不将识别不清的数值直接存为确定事实。
- 清楚处理麦克风拒绝、无语音、设备不可用、网络失败、超时和浏览器不支持，保留文字输入。
- 实施时核验目标浏览器能力；若不能稳定识别，接入明确配置的录音转写服务作为替代。现有聊天模型不等于具备音频转写能力，不能假定现有服务支持。
- 原始音频默认不长期保存；使用远程转写时说明音频发送用途。当前要求是语音识别输入，不包含语音播报或实时双向通话。

语音验收必须包含真实麦克风端到端测试及失败路径，不能只检查按钮或脚本语法。自动化可用虚构音频测试转写和后续业务，但不能替代麦克风权限与收音验收。

### 对话：自然语言操作入口

- 文字、语音和照片入口保留。一次输入可同时更新资料、记录实际事件、生成计划。
- 回复由简短解释、保存结果卡、计划卡或一个必要追问组成。
- 卡片明确显示“已更新档案”“已记录”“计划已生成”“待核实”“保存失败”，附查看、修改、撤销。
- 模型输出成功但存储失败时不得显示已保存；提供重试且防止重复创建。
- 新对话清空短期上下文，不清空个人档案、当前计划、目标和执行反馈。

### 看板：当前计划与今天的执行入口

内容优先级：

1. 当前计划：名称、目标、建议中/执行中状态、适用日期、版本、查看完整计划。
2. 今天的安排：计划项、执行时间或场景、完成/部分完成/跳过/延期操作。没有约定具体钟点时显示场景，不虚构固定作息。
3. 最新状态：体重、睡眠等真实数据，明确测量日期和缺失项。
4. 执行反馈：已完成、未反馈、部分完成；只对有明确数量目标的事项计算比例，并显示分母。
5. 调整与复盘：为何建议调整、受哪些记录影响、何时复盘。

建议计划尚未启用时，仍展示计划内容和“开始执行”；不能回退成一张通用睡眠建议卡。没有计划时给出“通过对话制定计划”，没有数据时显示暂无记录。

看板由持久数据计算和读取，打开页面不重新调用模型生成另一套安排。跨日仅按已有有效计划产生当天事项，不能每天悄悄重写计划。

### 档案：完整个人健康信息中心

- 我的概况：基本资料、最近一次体重/腰围及日期、当前目标、资料待补充项。
- 健康背景：用户自述疾病、手术、过敏、用药信息及核实状态。
- 生活习惯与约束：职业、作息、饮食偏好、可用时间、可接受活动方式。
- 历史记录：按实际发生时间查看体重、睡眠、饮食、症状、报告和执行反馈。
- 目标与计划历史：当前计划、旧版本、调整原因、阶段复盘。
- 来源与管理：从任一字段或记录回到原对话，修改、删除、纠错、控制是否用于模型记忆。

“我的”只保留使用设置、隐私和保存偏好、备份恢复、模型连接状态。健康资料迁移到档案，原入口可跳转到同一个编辑界面，避免维护两份数据。

## 6. 端到端使用流程

### 场景 A：从一句话建立档案并生成计划

虚构输入：“我38岁，175厘米，今天85公斤，长期久坐，主要吃外卖，不太喜欢运动，帮我做个先执行一周的计划。”

1. 分别识别本人资料、今日体重、生活偏好、计划请求和一周期限。
2. 已有资料可用时不再重复问；仅对确实影响下一步的缺口追问一个问题。
3. 可以形成初步安排时直接生成，标出依据和待补充项；不能以全部资料齐全为门槛。
4. 保存档案、测量事件、关联目标、计划；依据用户执行意图设为执行中。
5. 对话显示此次保存结果与计划卡；看板显示当前一周计划和今日事项；档案展示本人资料、体重和偏好。
6. 刷新、重新打开、新建对话后，三处一致，且能继续调整这份计划。

旧需求中的示例用户画像仅是测试背景，不能自动写入任何新用户档案，也不能凭身高体重推断疾病。

### 场景 B：只有一句“帮我制定计划”

有档案：读取已有目标、生活约束和当前计划，生成适用的建议计划并持久展示。

无档案：先确认希望解决的问题；能提供初步安排时生成“初步计划”，明确未知项。一次一个关键问题，表单是可选辅助，不是必经入口。

### 场景 C：执行反馈与计划调整

“今天午饭按计划吃了，活动只做了一半” → 关联今日具体计划项，分别保存完成与部分完成；事实不足时不虚构热量或运动时长。

“明天出差，安排简单点” → 生成仅适用于明天的覆盖安排，显示变化和原因，不覆盖今天的执行记录和以后所有日期。

“以后都改成晚上” → 更新后续生效的计划版本，保留历史；不能更改已经完成事项的原定时间。

### 场景 D：纠错、拒绝和暂不保存

“刚才说的是昨天，不是今天” → 修改原记录发生日期，相关看板重新计算，不再新增同一事实。

“这条别记”“这里只是假设” → 不生成长期档案事实；已关联的错误变更可撤销。

“这个计划不合适” → 询问不合适之处；保留当前状态直到用户明确暂停、替换或撤销。

## 7. 计划的最低完整结构

计划必须包含：

- 身份：plan_id、version、名称、领域、状态（建议中、执行中、暂停、完成、已替换）。
- 目标：目标描述、可选衡量指标、时间范围、关联 goal_id。
- 依据：引用的档案字段、记录 ID、来源消息、使用的数据版本，未知项。
- 计划项：稳定 item_id、行动描述、日期/周期/场景、最低可执行方式、可选替代方案、完成口径。
- 跟进：复盘日期或触发条件、调整原因、前一版本、创建和生效时间。

用户没提供可量化目标时允许定性计划；不要求所有计划都填热量、目标体重或固定时间。

建议中 → 执行中 → 暂停/完成；调整形成新版本，旧版本标记已替换。是否完成阶段目标由证据和用户确认决定，不能只因日期到期就宣称目标完成。

每日任务实例独立于计划模板：plan_id + version + item_id + 当地日期唯一；执行事件引用该实例。已过期事项无反馈时显示未反馈，不计为失败。

## 8. 技术实施方案

### 服务端统一编排

处理请求 → 定位用户/会话与目标计划 → 加载已确认事实、当前计划和近期反馈 → 解析意图与候选动作 → 校验主体、时间、数值和权限 → 事务保存 → 返回结果卡和刷新所需数据。

模型负责理解和生成候选业务动作；程序负责动作白名单、参数校验、ID、版本、幂等、存储和状态转换。不能执行模型返回的任意路径、代码或接口名。

建议结构化结果：reply、profile_changes、record_events、goal_changes、plan_proposals、plan_changes、execution_events、clarification。来源消息 ID 由服务端绑定，不能信任模型伪造来源。

每次提交带 request_id/client_message_id，重试返回原结果；后端一次事务写入消息、变更和回执，避免前端再调用单独接口才保存关键业务结果。

模型请求在事务外进行。开始时记录相关数据版本，提交前检测变化；其他对话已更新同一计划时提示冲突或重新合并，不以旧模型结果覆盖新版本。

### 存储建议

推荐转为本机 SQLite，保持单用户本地部署，获得跨对象事务、唯一约束、版本检查和查询能力。不要靠新增多个 JSON 文件模拟事务。

主要表：profile_fields、profile_changes、health_records、goals、plans、plan_items、task_instances、execution_events、conversations、messages、action_receipts、pending_changes、media。

- profile_fields 保存值、主体、来源、有效时间、核实状态；覆盖前保存变更历史。
- health_records 分离 occurred_at（发生）和 created_at（录入），保存单位与修正链。
- pending_changes 持久化歧义和待确认项，刷新后仍能处理。
- 对话摘要仅是派生内容；计划和档案以业务数据为准。
- 撤销按变更与版本执行；如后续内容已依赖该变更，提示影响或创建纠正版本，不能简单删除旧值。

迁移：备份现有 JSON/原图 → 在隔离数据库导入并核对数量与引用 → 验证备份恢复 → 切换读写。保留旧文件用于回滚；不把旧聊天模型建议自动当成已生效计划。历史提取作为单独、可预览的补录功能。

现有备份只识别旧 JSON 文件，必须随数据库方案升级备份格式和恢复验证；使用 SQLite 一致性备份能力，不直接拷贝正在写入的数据库文件。

### 接口与前端

- `/api/chat`：统一持久保存消息和业务动作，返回保存回执、计划卡、待核实项。
- `/api/bootstrap`：一次返回档案摘要、当前计划、今日事项、实际指标和待处理项。
- `/api/plans` 及详情/启用/暂停/调整接口：持久计划查询与生命周期管理。
- `/api/tasks/.../feedback`：记录执行结果及撤销；自然语言和按钮共用相同业务服务。
- `/api/profile`、记录和导出接口：保留必要兼容层，统一读新存储。

前端按对话、看板、档案、设置、共享卡片和 API 客户端拆模块；由同一份服务器状态驱动页面。先保证完整闭环，再做视觉美化。

## 9. 实施顺序与验收门槛

| 阶段 | 交付内容 | 可以验收的用户结果 |
|---|---|---|
| P0-1 数据和事务底座 | 对象模型、迁移、幂等、计划状态、备份兼容 | 一次保存后能重读，重试不重复，失败不留下半份档案 |
| P0-2 第一条完整链路 | 对话资料提取 + 计划生成保存 + 看板计划卡 + 档案概况 | 场景 A 一次走通，刷新和新对话仍然存在 |
| P0-2 补充输入方式 | 按问题选择表单、持久采集状态、中文语音识别及失败处理 | 表单或语音补充后继续原始计划请求，三种输入生成相同业务结果 |
| P0-3 跟进闭环 | 今日事项、自然语言反馈、按钮反馈、计划版本调整 | 做完事项能更新；临时调整不破坏历史 |
| P0-4 真实验收 | 浏览器端到端回归、故障重试、隔离真模型验证 | 用户能在界面看见计划/档案/反馈，不只检查 HTTP 200 |
| P1 深化 | 图片提取接入相同动作流、阶段复盘、报告整理、历史补录 | 多模态和历史数据也能进入同一套业务对象 |
| 后续 | 主动通知、设备、多人账户、部署级运维 | 不作为第一条产品闭环的前置条件 |

第一条验收链路完成之前，不再以增加运维功能代替产品交付。自动备份等现有能力保留。

## 10. 必须覆盖的验收场景

1. 一条消息同时产生个人资料、体重记录和可见计划，三处显示一致。
2. “制定计划”生成建议计划；“从今天执行”生成或激活执行计划，两种都在看板可见。
3. 档案不足时一次只问一个关键问题；已说过的信息不要求反复填表。
4. 目标体重不覆盖当前体重，计划事项不进入已完成记录。
5. 假设、家人信息、不确定诊断不成为本人已确认事实。
6. 修改日期、单位或刚才的口误，修正原事实，不产生重复事件。
7. 重复点击、超时重试只产生一份计划/一条执行记录。
8. 数据写入失败时没有“已保存”回执；模型失败时不生成伪计划。
9. 刷新、新对话、服务重启后计划、档案、待核实项和执行状态保持一致。
10. 明天临时调整只影响明天；旧版本、已完成事项和来源仍可查。
11. 同时打开两个页面更新同一计划，旧结果不能覆盖新版本。
12. 跨日后今日事项正确切换；昨天未反馈不自动变失败；没有约定时间不虚构精确时间。
13. 备份恢复包含所有新增对象和媒体；原 JSON 导入不丢失已有正式资料。
14. 用户撤销或禁止某项记忆后，后续回答遵守；衍生摘要不能绕过记忆设置。
15. 新用户分别询问减脂、睡眠和一般知识时，收到不同且相关的采集方式；不重复询问已提供项。
16. 表单提交或语音回答后继续原始请求；刷新仍保留已回答/跳过状态。
17. 中文语音可编辑后发送，生成的资料和计划与等价文字一致；取消和识别失败保留已有草稿。
18. 真实麦克风可收音；无权限、不支持浏览器和转写失败时给出可操作提示，不显示尚未实现的平台承诺。

## 11. 本轮结论

首要交付是“对话生成并保存计划和档案，切换页面立即可见，后续对话可以更新”，不是继续扩充聊天话术。现有系统需要业务模型与页面职责的同步改造，仅改提示词或给看板拼接一段模型回复不足以实现上述需求。
