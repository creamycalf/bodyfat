## 1. 产品目标与用户痛点

目标是能持续了解用户、帮助调整饮食的营养管理助手，不是拍照算热量加聊天框，也不冒充真人营养师或替代诊疗。

用户反复反馈：固定兜底话无法接话；结构化解析错误打断正常聊天；只说想减肚子就给方案；照片选择即上传，没有机会补充意图；多食物营养报告难看且缺乏明细和依据。

期望体验：自然咨询 → 记住必要资料 → 可修改的餐食报告 → 确认实际摄入 → 有依据的阶段复盘。

本轮规划原则：模型负责理解和交流，数据源提供依据，程序负责计算与可靠保存。不要继续用越来越长的单个提示词代替产品架构。

## 4. 实施顺序

### 第一阶段：自然咨询和可靠记忆（新任务先做这个）

1. 阅读代码并跑基线，列出目前问答、事实整理、计划生成、安全校验之间的实际依赖。
2. 将一般问答、单餐分析、个体方案、复盘、高风险问题区别处理。不能所有问题都先建档。
3. 将 consultation.py 的全字段硬门槛细化为与当前决策有关的必要信息。不能仅凭目标出个人方案，也不能用几十个必填字段阻止一切有帮助的回应。
4. 每轮先回应用户刚说的内容，再问1–2个能改变建议的问题；已知不重复问，冲突只核对冲突，允许跳过且明确未知。生活阶段等只在适用时询问。
5. 正式个人方案前，先总结已知事实、限制与待确认之处，请用户纠正；摘要确认必须有状态支持，不能仅写在提示词。
6. 区分用户明确事实、模型推测、待确认项、历史过期信息；保留来源和时间。修改/撤回后后续问答与计划应一致。
7. 逐步拆开面向用户的自然回复与后台结构化整理。后台失败保留正常有效回复并单独说明哪些操作未完成；不得伪称已保存。真实安全问题仍拦截。不要为拆分盲目增加多次串行模型调用，评估延迟、成本、幂等和一致性。
8. 保留现有数据、恢复、事实检查点和危险方案校验。不要用固定“请继续/完善资料”覆盖整段正常交流。

第一阶段验收场景：

- “我200斤，想减肚子”不立刻出完整食谱或强度计划，也不一次发长问卷。
- “38，172，男”结合上一问正确归档并自然续聊。
- “早餐一杯牛奶两个鸡蛋”不再次问早餐吃什么；缺的是份量或其他真正相关信息时再问。
- 已说不愿提供某项后，不在每轮追问；未知不等于无病或无禁忌。
- 中途问一餐/普通科普能直接回应，再允许回到咨询主线。
- “那是我爸的报告”“刚才说错了”“还没吃”“吃了一半”不污染本人的事实。
- 结构化整理失败、超时重试不丢原话、不重复记账、不误称计划已生成。
- 完整资料场景能走到摘要核对和可保存方案，避免只测试阻止生成。
- 正常新旧会话都能续接，不要求用户重说整套档案。

以独立模块和回归测试落实，不只改提示词。阶段完成后报告已实现、测试证据、剩余限制，并更新交接文档。

### 第二阶段：有来源、可修正的营养计算

识别候选→食物匹配→核对份量→本地计算→报告→确认实际食用。

- 数据优先采用可核对标签、匹配正确的数据库条目；模型估计单列来源级别，不能伪造引用。
- 保存 source/id/version、每100g还是每份、生熟与可食口径、重量依据。单位严格换算。
- 处理混合菜和隐含油酱；避免整道菜与组成重复计数；未知项不当零。
- 报告支持改食物、重量、几人份、实际吃多少，局部重算；保存常吃食物以减少重复核对。
- 数据库无结果或断网时降级透明。新增服务、费用、许可或外部数据传输超出当前配置时先说明并取得所需选择。
- 建立真实中餐/标签核验集，分开评估识别、份量、数据库匹配、算术，不能用UI测试代替准确性测试。

### 第三阶段：持续跟进与阶段复盘

- 从一两个优先习惯开始，根据用户真实记录调整，不每次推翻全部方案。
- 同时考虑饥饿感、执行困难、睡眠、活动和趋势；漏记不算没吃，一天波动不直接导出限制。
- 每次调整说明依据、未知、变化和观察条件，保留计划版本与历史执行记录。
- 病史、药物和报告信息只作为适当边界与就医沟通依据，不自行诊断或改药。

### 第四阶段：可执行餐单、外卖与购物清单

结合已知偏好、预算、过敏、做饭条件、时间设计可替换选项。菜谱是建议，不是实际摄入。暂不优先增加自训练视觉模型、花哨评分和大量新页面。
